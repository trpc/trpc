# oRPC parity matrix

**Goal from the [brief](../decisions/brief.md):** feature parity with [orpc.dev/docs/comparison](https://orpc.dev/docs/comparison). Any API decision that could stop us from getting there must be flagged and confirmed by a human before it is accepted. Since round two, parity tracks oRPC v2's table ([orpc-v2-parity](../decisions/orpc-v2-parity.md)).

Source: oRPC v2's [`apps/content/docs/comparison.mdx`](https://github.com/middleapi/orpc/blob/v2.0.0-beta.44/apps/content/docs/comparison.mdx), row for row and in its groups. The oRPC and tRPC v11 columns are copied from it; the v11 column is oRPC's assessment and may lag behind v11. The v12 column is what `next/` ships, each row covered by integration tests with real clients. Unreviewed calls are the `(agent)` decisions: `pnpm decisions --who agent`.

Legend: ✅ first-class · 🟡 partial / third-party · 🛑 not supported. `experimental_` exports may still change ([stability-jsdoc-tags](../decisions/stability-jsdoc-tags.md)).

## Performance

oRPC's table compares oRPC v2 with v11 (and Hono). `pnpm bench` measures the same way with v12 added; method and caveats in [`../notes/benchmarks.md`](../notes/benchmarks.md).

| Metric                                    | oRPC v2           | v11               | v12                 |
| ----------------------------------------- | ----------------- | ----------------- | ------------------- |
| RPC over HTTP (req/s avg)                 | 63,594            | 15,533            | 48,845              |
| Type-check, 3,000 procedures (check time) | 0.68s             | 0.97s             | 0.99s               |
| Type-check, 3,000 procedures (memory)     | 174 MB            | 195 MB            | 246 MB              |
| Client bundle (minified / gzip)           | 27.1 kB / 9.6 kB  | 36.4 kB / 11.8 kB | 132.3 kB / 43.9 kB  |
| Node server bundle (minified / gzip)      | 41.3 kB / 13.2 kB | 53.1 kB / 17.3 kB | 364.6 kB / 117.8 kB |

- v12 beats v11 on throughput, is level with it on check time ([`../notes/type-check-shapes.md`](../notes/type-check-shapes.md) has where the types grew), and trails oRPC on every row. The rows are `next/www/benchmarks.json`, measured 2026-10-20 on Node 26 and TypeScript 7.1 at the commit it names, which the docs' hidden benchmarks page charts ([`benchmarks-page.md`](../decisions/benchmarks-page.md)).
- The floors are Effect's: its `HttpServer` alone does about 69k req/s; its declarations take about 65 MB of the type-check memory; the Effect APIs the client runs on are about 20 kB gzipped, and a one-element `Stream`, which every link returns, is 10.7 kB on its own. CI reports the client's gzip sizes, without ceilings, against the human's targets (18 kB minimal JSON, 25 kB full; [`../notes/benchmarks.md`](../notes/benchmarks.md#budgets)).

Not measured yet: RPC over WebSocket, OpenAPI over HTTP, Clinic profiles.

## The decisions that matter most for parity

Get these right and every other row is incremental work:

1. **Split contract from implementation in the procedure data model** (03, 09). Contract-first, OpenAPI links, NestJS and client-side validation all depend on it.
2. **Put serialization on endpoints, not on the router** (11). One router must be servable by an RPC endpoint (rich serializer) _and_ an OpenAPI endpoint (plain JSON) at the same time.
3. **Keep the protocol and handler transport-agnostic** (10, 12). HTTP, WebSocket and MessagePort share one message model.
4. **Allow per-procedure HTTP routing metadata** (04, 18): `.meta({ route: { method, path, … } })` under the `experimental_openapi()` root extension ([root-extensions](../decisions/root-extensions.md)).

## MCP compared with `@orpc/mcp`

oRPC shipped `@orpc/mcp` on 2026-10-21 ([docs](https://orpc.dev/docs/integrations/mcp)); `@trpc12/trpc/mcp` is experimental, and proposal 25's questions are open ([`../open/`](../open/)).

- Matched from oRPC: the title from `route.summary`, the description falling back to it, `idempotentHint` for `PUT` and `DELETE` routes, annotations merged hint by hint across `.meta()` calls, `icons`, lazy subtrees loaded on first use, a non-object input under `input`, and errors as `isError` results with `{ defined, code, message, data }` and unexpected ones masked.
- Different by design: oRPC publishes every procedure, v12 only those with `mcp` meta unless `include: 'all'`; oRPC registers tools on the MCP SDK v2's `McpServer`, so any of its transports and sessions work, while v12 speaks stateless Streamable HTTP itself with no SDK dependency; v12 hides tools per caller with `filter({ tool, ctx })` and answers `createContext`'s `UNAUTHORIZED` with a `401` and `WWW-Authenticate`.
- oRPC has, v12 doesn't yet: `operationId` as the tool name; `Blob` and `File` outputs as image, audio or resource content; a streamed output's last event as the result, with every event as progress (v12 refuses streamed outputs and leaves subscriptions out); smart coercion of tool arguments by plugin (v12 needs `z.coerce.date()`); interceptors and plugins around each tool call (v12 has middleware, `onError` and spans); per-tool-call context from the MCP request context (v12 makes it per HTTP request).

## Maintenance

- When a decision changes a row, update the row in the same commit.
- If a decision would turn a row into 🛑, the agent must stop and ask a human (see `../approach.md`).
- Re-check against `comparison.mdx` when bumping the vendored oRPC version, and re-run `pnpm bench` when the Performance rows could have moved.
