# Effect middleware's `next()` fails with the downstream error (human asked)

- The question (first-release review, question 3): Effect middleware's `next()` didn't fail with the downstream error. It succeeded with a `MiddlewareResult` whose `ok` was false, unlike `effect/rpc`'s `RpcMiddleware`, where `next` fails, so `Effect.catchTag('NOT_FOUND')`, `Effect.retry` and `Effect.timeout` on `next()` didn't see procedure failures. A) keep the result form (shared with Promise middleware, cheap) and document "check `result.ok`"; B) make `next()` fail with the error union: more idiomatic, but splits the two middleware kinds.
- Human, 2026-10-19 (first-release review, question 3): "idk, make the best DX".
- (agent) B for Effect middleware, A stays for Promise middleware. Effect `next()` is `Effect<NextResult<$Ctx, $Input>, NextError, Provides>`: it succeeds with `{ ok: true, data }` and fails with a `NextError`, the `TrpcError` clients will get (a thrown value is an `INTERNAL_SERVER_ERROR`, a thrown declared code is typed, as in the result form). Interruption stays interruption. Promise `next()` still resolves to `{ ok, data | error }`, as in v11.
- (agent) The tasks, Effect middleware, A then B:
  - logging an outcome: `Effect.tap(next(), (r) => log(r.ok))` vs `Effect.onExit(next(), (exit) => log(Exit.isSuccess(exit)))`, or `Effect.tapError`;
  - mapping a downstream error: `Effect.flatMap(next(), (r) => !r.ok && r.error.code === 'NOT_FOUND' ? Effect.fail(new Gone()) : Effect.succeed(r))` vs `Effect.catchTag('NOT_FOUND', () => Effect.fail(new Gone()))`;
  - retrying: a hand-rolled `Effect.repeat` on `!r.ok` vs `Effect.retry({ times: 2, while: (e) => e.code === 'SERVICE_UNAVAILABLE' })`;
  - timing out: `Effect.timeoutOrElse` works in both (it interrupts); a bare `Effect.timeout` is a type error in both until its `TimeoutError` is mapped;
  - transactions: under A, `Effect.acquireUseRelease(begin, (tx) => next(), (tx, exit) => …)` committed failed calls (`exit` was a success; `effect-middleware.test.ts` showed `['commit 1', 'commit 2', 'commit 3']` on the old runtime), and only `acquireRelease` worked, because the step's `Scope` also wraps the result check; under B both roll back;
  - auth before `next()` and ctx for `next()`: the same in both; `user ? next({ ctx: { user } }) : Effect.fail(err)` keeps both branches' types (see below);
  - reading the output: `r.ok ? r.data : …` vs `r.data`. `Effect.exit(next())` gives A's form back when it's wanted.
- (agent) Prior art: `effect/rpc`'s `RpcMiddleware` gets `Effect<SuccessValue, E | unhandled, Provides>` (`.repos/effect/packages/effect/src/rpc/RpcMiddleware.ts`): it fails, with the downstream errors behind the opaque `unhandled`, so `catchTag` can't name them. `HttpApiMiddleware` is the same with `HttpServerResponse` and `unhandled`; `HttpMiddleware` is generic in the app's `E`. oRPC's `next()` (`.repos/orpc/packages/server/src/middleware.ts`) resolves to `{ output, context }` and rejects with the error. v11 and our Promise middleware are the only result forms. `NextError` is `TrpcError<string, unknown>` with a phantom `'~next'`, so unlike `unhandled` it takes `catchTag`, `e.code` and `e.data`.
- (agent) Errors from middleware are still inferred into the procedure's union: the factory drops `NextError` from the body's failures (`Exclude<…, NextError>`), since the step that failed put its error there already; what a middleware maps it to joins. At runtime an error from `next()` that the body fails with again (or a Promise middleware returns) fails with its original cause, so a crash stays masked and a thrown code keeps `defined: false`; this replaces the `MIDDLEWARE_CAUSE` symbol on results.
- (agent) The factory now infers the body's whole `Effect` (`$Body`) and reads ctx, input, `ok()` values, errors and requirements from it. Inferring `E` itself, as before, picks one branch's error when a ternary returns two Effects (TypeScript takes the first candidate when neither is a supertype; `Effect.flatMap` has the same limit), which a failing `next()` made common: `ctx.user ? next() : Effect.fail(err)`.
- (agent) Numbers (`pnpm bench shapes`, 1,500 procedures, new `effect middleware` shape: the `middleware` shape plus an Effect middleware with `Effect.tapError`): 1,168 → 1,187 instantiations per procedure on the server (+1.6%), types 164,825 → 158,866, memory 275 → 270 MB; with the client 1,489 → 1,508. The `middleware` and `effect` shapes don't change.
- (agent, 2026-10-19, fix) A Promise middleware's `next()` runs the rest of the chain on a fiber of its own, which only the call's `signal` interrupted, so `Effect.timeout` (or any interruption) around an earlier Effect middleware's `next()` left the resolver behind a Promise middleware running. The Promise step now runs in `Effect.callback`, and `next()` runs with its interrupt-bound signal (`attempt` in `execute.ts`); the one Promise bridge is still `Effect.runPromiseExitWith` at `next()`. Tested in `effect-middleware.test.ts` ("interrupting next() reaches the steps after a Promise middleware").
- Why: every Effect combinator that reacts to failure (`catchTag`, `retry`, `tapError`, `onExit`, `acquireUseRelease`) works on `next()` as it does on any Effect, and the transaction footgun is gone. The two kinds already differed in what `next()` returns; each now follows its own world's idiom (Effect fails, Promise resolves to a result as in v11).
- Lost: one shape for both kinds (a helper written against `MiddlewareResult` doesn't take an Effect `next()` as is; `Effect.exit` bridges it); `NextError`'s `_tag` is `string`, so `catchTag` doesn't autocomplete codes and a typo isn't caught (the downstream union isn't known where a middleware is written); a mapped error leaves the original code in the union (`catchTag('NOT_FOUND', … PostGone)` gives `NOT_FOUND | POST_GONE`), as `RpcMiddleware` can't subtract either.
- Open: Promise `next()` rejecting instead (oRPC's form) wasn't considered for v1: it would break v11 middleware and the lifecycle helpers. Middleware as an Effect service (Q27.3, `spikes/layered-services/middleware-service.ts`) now types its `next` with `NextError` too.
- Lives in: `packages/trpc/src/server/procedures/middleware.ts` (`NextResult`, `NextError`, `EffectNextFn`, `EffectMiddlewareFactory`), `src/server/execution/execute.ts` (`failNext`, `middlewareCause`, `nextCauses`), `src/middleware/durable.ts`, `packages/trpc/src/server/procedures/effect-middleware.test.ts`, `www/docs/server/effect.md#around-next`, `www/docs/server/middleware.md#effect-middleware`, `tooling/bench/shapes.ts` (`effect middleware`).
