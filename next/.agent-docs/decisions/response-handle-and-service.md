# Response headers and status: a handle, and an Effect service over it (human)

- Human, 2026-10-15 (decisions round 3, Q6 = proposal 04 Q4.2): "C".
- Promise resolvers and middleware keep the mutable `response` handle (`response.headers.set(…)`, `response.status = 201`).
- Effect code uses a service over the same handle: `yield* Response.setHeader('cache-control', 'max-age=60')`, `Response.setStatus(201)`, `Response.appendHeader('set-cookie', …)`.
- In a batch, headers merge (`set-cookie` appends) and each call's status stays in its own line.
- (human asked) Batched responses always sent `cache-control: no-cache`: the JSONL and SSE defaults were spread over the calls' headers, and the merge kept the last call's `cache-control`. Human, 2026-10-18: "seems like a bug that batching forces that". A batch's `cache-control` is now the strictest policy every call allows (`strictestCacheControl`): `no-store`, then `no-cache`, from any call wins; `private` beats `public`, which needs every call; `max-age`, `s-maxage` (falling back to `max-age`) and the `stale-*` lifetimes take the smallest; a lifetime that isn't a number is `0`; unknown directives drop. A call that sets none, an error included, leaves the batch at the default `no-cache`. Streamed responses keep a call's own `cache-control`, and `vary: accept` adds to a call's `vary` instead of replacing it. The v11 handler merges its batches the same way; there it matters most, since v11 batches queries over `GET`. RPC batches are `POST`, which shared caches don't store, so the header there speaks to browsers and caches set up for it.
- Why: Effect code reads its dependencies from services, matching [`internals-use-effect.md`](./internals-use-effect.md) and the `effect/http` core ([`http-core-on-effect-http.md`](./http-core-on-effect-http.md)); Promise code keeps the simple handle.
- Lost: a return-value wrapper (`withResponse(value, …)`), which tests more easily but stops middleware from adding headers.
- (agent) The root provides the service, so procedures using it don't add a layer requirement.
- Lives in: `packages/trpc/src/server/execution/response.ts`, `src/server/execution/execute.ts`, `src/server/procedures/middleware.ts`, `src/server/handler/cache-control.ts` (the batch's `cache-control`); tests in `packages/trpc/src/http/core.test.ts`, `src/server/handler/cache-control.test.ts`, `src/interop/handler/handler-edges.test.ts`.
