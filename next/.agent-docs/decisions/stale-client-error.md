# A procedure the server lacks stays a built-in `NOT_FOUND`, with no stale-client code, for now (human)

- Human, 2026-10-20 (Q24.7): "A", keep it as it is, for now. That is the open question's A, proposal 24's C ("later").
- A client built against a newer router (a deploy in progress, a cached bundle) that calls a path the server doesn't have gets `NOT_FOUND`, `No procedure at path "<path>"`, as a built-in error (`defined: false`). `matchError()` sends it to `unexpected`.
- (agent) Since [error-tags](./error-tags.md), that error is tagged `ProcedureNotFound`, and the tag goes on the wire. It is still a built-in `NOT_FOUND`, with no new code, header or fingerprint, so this answer stands. An app that wants a reload prompt checks `err._tag === 'ProcedureNotFound'` (inside `case 'NOT_FOUND'`, or in `unexpected`), and Effect code catches it alone with `Effect.catchTag('ProcedureNotFound')`, apart from the declared `NotFound`. It doesn't say the client is stale for certain: an untyped client's typo gets it too.
- Why: it's independent of the rest of proposal 24 and wasn't spiked, and keeping it needs no new code, header or wire field.
- Lost:
  - B, a distinct error for unknown paths: the server sends `NOT_FOUND` with `data: { procedure: path }`, and the client turns it into a new client-side built-in code, `STALE_CLIENT` (status 0, like `BAD_RESPONSE`). Small, with no header and no hash, and v11 clients and OpenAPI callers still see a plain `NOT_FOUND`. But it also fires for a typo in an untyped client's path, and a thrown `NOT_FOUND` with that `data` shape would be misread unless the key is reserved.
  - C, a router fingerprint: the client sends a hash of the router's paths and types in a `trpc-router` header, and a server whose hash differs answers unknown paths with `STALE_CLIENT`. It knows the cause for certain, and could later flag a changed type on a path that still exists. But a types-only client (`routerType<AppRouter>()`) has no router at runtime, so the hash needs a build step or a contract, and a custom header on every request forces a CORS preflight, which tRPC avoids today.
  - So a stale deploy looked like a missing record unless the app checked `defined` or matched on `message`, until the `ProcedureNotFound` tag.
- Open: when this comes back, B is the cheaper path: no header, and nothing changes for v11 or OpenAPI callers. It would read `data.procedure` before `fromWireError` folds built-in errors through `toUntypedError` ([closed-client-errors](./closed-client-errors.md)), or keep it for that one shape, and reserve the key. The `ProcedureNotFound` tag already tells a missing procedure from a missing record ([error-tags](./error-tags.md), [granular-errors](./granular-errors.md)); B would add `STALE_CLIENT` on top of it.
- Lives in: unknown paths are answered in `packages/trpc/src/server/handler/call.ts` and `batch.ts`, `src/server/sockets/socket.ts` and `src/client/links/local.ts` (`No procedure found on path` in the v11 interop handler, `src/interop/handler/handler.ts`); documented in `www/docs/client/errors.md` (switching on the code) and `www/docs/client/effect.md`; proposal in `proposals/24-error-ownership.md`; census in `notes/closed-error-unions.md`.
