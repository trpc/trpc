# `inferRouterOutputs` is what a client receives: a client's type follows its links, a router type is plain JSON (human asked)

- The question (first-release review, question 8): `inferRouterOutputs<AppRouter>` gave the server's types (`createdAt: Date`) while a client without a serializer receives a `string`; v11's applied the transformer. The review recommended documenting it and adding an `experimental_inferClientOutputs`.
- Human, 2026-10-19 (first-release review, question 8): "should we really have both?"
- (agent) No, one helper. `inferRouterOutputs<T>` is what a client receives, by path, which is what v11's meant:
  - `T` a client's type, or a client factory's (`typeof makeClient`, as `createTrpcContext<T>()` takes): outputs follow its links, through the same `ResultForm` its calls use. danSON and superjson-style serializers keep `Date`, `experimental_openApiLink` is JSON, `createRouterClient` keeps native types.
  - `T` a router type: plain JSON's form (`Date` → `string`, `Map`/`Set` → `{}`, `undefined` keys optional, `bigint` → `never`), the default serializer's, as `TrpcClient<AppRouter>` and `createTrpcContext<AppRouter>()` already type it.
- (agent) The router can't "follow its serializer": since Q11.5 the serializer is on the handler and the links, not `initTrpc` ([`replaceable-serializers.md`](./replaceable-serializers.md)), so a router type has none to read. A client's type records its links' form (`ClientTypes`), so it is the source.
- (agent) `inferProcedureOutput<P>` stays the output as the procedure returns it, for server code. `inferRouterInputs<T>` takes the same sources; the serializer doesn't change what a client's calls take, so it is the router's inputs either way.
- (agent) The codemod notes each `inferRouterOutputs` import (v11 projects with a transformer get strings now); the migration table has the row.
- (agent) Cost, `pnpm bench shapes --only plain,infer` (1,500 procedures, each result annotated with `Outputs['f0']['p0']`), with client: 979,001 instantiations with the old server-types helper over the router, 993,449 for the router's JSON form (+1.5%, about 10 per procedure), 994,297 from `typeof client`; 0.8 s each. The unannotated `plain` shape is 957,221.
- Why: one name answers "what does my client get"; the client's type already knows the form, and a router type alone gets the default's, as everywhere else.
- Lost: `inferRouterOutputs<AppRouter>` as the server's types (use `inferProcedureOutput` per procedure, or `inferRouterOutputs<typeof caller>` over `createRouterClient`). A second type parameter naming the serializer (`inferRouterOutputs<AppRouter, typeof serializer>`) was set aside: it repeats what the client's type records, and can disagree with links that change the form (`experimental_openApiLink`, `experimental_validationLink`). A separate `experimental_inferClientOutputs` was set aside for the human's reason: two helpers for one question.
- Open: `inferRouterErrors` is still the server's error union (`data` not in the form); an input that JSON can't carry (a `z.date()` input over plain JSON) is typed as the schema's input, by the client and here.
- Lives in: `packages/trpc/src/server/procedures/router.ts` (`inferRouterOutputs`, `inferRouterInputs`, `SourceClient`), `packages/trpc/src/serializer/serializers.test.ts`, `packages/upgrade/src/transform.ts` (`NAME_NOTES`), `tooling/bench/shapes.ts` (`infer`), `www/docs/client/overview.md#inferring-types`, `www/docs/server/serializers.md`, `www/docs/migrations/from-v11/api-changes.md`, `www/docs/migrations/from-v11/codemod.md`.
