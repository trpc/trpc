# SSE subscriptions move make-before-break on a server's reconnect (human asked)

- Human, 2026-11-05, relayed: "SSE has no reconnect signal today: `maxDurationMs` just ends the stream, and `reconnectAfterInactivityMs` is client-side. Add a server "reconnect" event sent shortly before `maxDurationMs` runs out (and usable for graceful shutdown). The client opens the new stream with lastEventId while the old one keeps delivering, and switches once the new one sends `connected`. The inactivity timeout stays break-before-make."
- (agent) Every RPC SSE stream starts with `event: connected`, in place of the `: open` comment ([`fetch-sse.md`](./fetch-sse.md)); it flushes the headers the same way. `EventSource` ignores both named events. The OpenAPI handler's streams keep `: open`.
- (agent) `createFetchHandler({ sse: { maxDuration, reconnectNotice } })`: `reconnectNotice` (`'5 seconds'`) before `maxDuration`, the stream sends `event: reconnect`, and at `maxDuration` it ends without `done`. No `maxDuration` by default. A notice longer than `maxDuration` is sent at once.
- (agent) Each stream joins the handler's `SocketDrains`, so `drain()`, `dispose()` and `serve()`'s shutdown send `reconnect`, wait for the client to leave up to the drain's timeout, then end the stream without `done`. `dispose()` no longer interrupts event streams first. A stream that starts during a drain isn't registered, so a client doesn't bounce back to the draining server; it ends when the handler closes.
- (agent) `httpLink` matches the `wsLink` switchover ([`ws-graceful-switchover.md`](./ws-graceful-switchover.md)): on `reconnect` it opens a stream with `Last-Event-ID`, and the old one keeps delivering until the new one's first event (`connected`). It drops the new stream's resends of ids the old one delivered meanwhile. A subscription whose new stream was opened without `Last-Event-ID` keeps the old stream after the move and delivers its events, at least once, until it ends (`done`, an error, or the server closing it at its drain timeout or `maxDuration`): the server writes `connected` before the resolver listens, and an aborted request has no stop confirmation to wait for, so aborting at once dropped events only the old stream had. A new stream that fails, a server error response included, leaves the old one delivering and is retried with `reconnect.delay`, without counting toward `reconnect.attempts`. An old stream that ends mid-move leaves the subscription on the new one; one that ends while no new stream is opening reconnects as before. `{ reconnect: false }` ignores `reconnect`.
- (agent) v12's `httpLink` has no inactivity timeout, so there's nothing to keep break-before-make there.
- Why: platforms cap response time (serverless limits, proxies), and a rolling deploy ends streams; a notice lets the client move without a gap or a visible reconnect.
- Lost: ending streams at once on `dispose()`, which made every SSE client reconnect blind with backoff.
- Open: whether new SSE requests should get a 503 during a drain, as WebSocket upgrades do. `httpLink` fails a subscription on a 503 from its first request, so this would need the link to retry one.
- Lives in: `packages/trpc/src/server/handler/subscription.ts`, `src/server/handler/http-handler.ts` (`sseLifetime`, `drains`), `src/server/handler/core.ts` (`close`), `src/server/handler/fetch.ts` (options), `src/client/links/http/sse.ts`, `src/internal/protocol.ts` (`SSE_EVENT`); tests in `src/server/handler/sse-drain.test.ts` and `src/client/links/sse-reconnect.test.ts`.
