# `createV11Handler` serves a v12 router to `@trpc/client` 11 apps (human asked)

- Human, 2026-10-15 (decisions round 3, Q3): "we'll provide codemods, migration guides, and special interop request handlers for old clients so you can deploy without risking to break the old apps". Closes the interop-handler scope Open in [`no-backwards-compatibility-yet.md`](./no-backwards-compatibility-yet.md).
- (agent) Scope is every v11 link, since a deployed app may use any of them: `httpLink`, `httpBatchLink`, `httpBatchStreamLink` (v11's JSON Lines with placeholders for promises and async iterables at the root or a top-level key), `httpSubscriptionLink` (SSE with `connected`, `ping`, `return` and `serialized-error` events) and `wsLink` (JSON-RPC envelopes, `subscription.stop`, `connectionParams`, `PING`/`PONG`). `FormData` becomes a bracket-notation object and `application/octet-stream` a `Blob`, so v12 schemas validate them.
- (agent) One handler, `createV11Handler` in a new `@trpc12/trpc/interop` entry, not a `protocol: 'v11'` option on `createFetchHandler`: the old protocol stays out of the v12 handler and is deleted in one place later. Same options as the v12 handlers (`createContext`, `layer`, `onError`, `middleware`, `exposeUnexpectedErrors`, `maxBodySize`) plus v11's `transformer`, `errorFormatter`, `batch` and `allowMethodOverride`.
- (agent) Effect-native first ([`effect-native-by-default.md`](./effect-native-by-default.md)): an `effect/http` app registered like `createFetchHandler`'s, so `serve()` runs it without web `Request`s; calls go through the shared `createHandlerCore` (masking, `onError`, spans, `response` handles). JSON Lines is a `Stream.callback` whose deferred values run in a `FiberSet`; a WebSocket's calls run in a `FiberMap` in the session's scope on Effect's `Socket` ([`websocket-sessions-on-effect-socket.md`](./websocket-sessions-on-effect-socket.md)), so `subscription.stop` and a closed socket interrupt them. v11's code was read for the wire format only.
- (agent) Errors take v11's shape (`{ message, code: <JSON-RPC number>, data: { code, httpStatus, path } }`). A v12 code v11 lacks becomes v11's code for its status (else `INTERNAL_SERVER_ERROR`) and keeps the status; `errorFormatter({ error, shape, path, type })` reproduces a v11 router's formatter with the v12 error at hand.
- (agent) Outputs go out as v11 sent them, `JSON.stringify` after the transformer's `serialize`, not through the output schema's JSON codec: the old apps' `AppRouter` types describe that form. The JSON links get the root's and top-level keys' promises settled; an async iterable needs `httpBatchStreamLink`, as in v11.
- (agent) A reconnect's `lastEventId` comes from the header, the query, or the input's `lastEventId` (where v11 clients put it) and reaches the resolver's `lastEventId` option. `createContext` runs per WebSocket call, as in v12, not once per connection.
- (agent) Secure defaults v11 lacked: batches are capped at 100 calls (`batch: { maxItems }`), the body at 1 MiB, and `tracked()` rejects ids with line breaks or NUL, which would forge SSE fields (for v12's SSE too).
- (agent, 2026-10-19) Shutdown: `dispose()`, and releasing `serve(legacy)`, close the open v11 WebSockets with 1012 ("service restart") before interrupting their calls, so no `stopped` result goes out. `wsLink` ends a subscription on `stopped`, but on a close it reconnects and resends the subscription with its last `tracked()` id. Before, `serve()` waited on open v11 sockets forever when it stopped (it only drained the v12 handler's), and `dispose()` left them running on a released `layer`. `serve()` finds any of our handlers' connections through `HandlerDrains` (`src/server/sockets/drain.ts`). v11's `reconnect` notification isn't sent: `wsLink` answers it by resending every pending request, mutations included.
- (agent, 2026-10-19) Effect-native internals:
  - JSON Lines reads a deferred value as progressive JSON does, through `sourceOf` (an async iterable through `Channel.fromAsyncIterableArray`, which keeps a generator's return value, and a promise through a `Deferred`). It used to wrap the iterator by hand to keep that return value, and use `Promise.resolve`.
  - An HTTP call's `AbortSignal` (`createContext`, the resolvers, then the SSE frames or JSON Lines it streams) comes from `interruptSignal()` in `internal/effects.ts`, as a socket call's does, instead of an `acquireRelease`d `AbortController` and a stream helper that each aborted it by hand.
  - `websocket()` forks on the handler core's `fork` (2026-10-20), with the handler's drains passed to `createHandlerCore`, so `dispose()` is the core's: the final drain closes each open session with 1012, then the sessions still running are interrupted. Interrupting one closes its socket with 1012 (`runWebSocketLike`), and a socket still connecting is closed once it opens, so no runtime throws on closing it early. Before, the session ran on `Effect.runFork` and outlived `dispose()`: a socket still connecting kept its listeners until it opened and was refused. A test in `socket.test.ts` pins the new behaviour.
- Responses match v11's byte for byte, but for a listed few, checked against `@trpc/server` 11 itself ([`v11-stream-cancel-and-interop-parity.md`](./v11-stream-cancel-and-interop-parity.md)).
- Lost: v11's `responseMeta` (procedures use their `response` handle), observable subscriptions (none exist on a v12 router), `experimental_encoder` WebSocket encoders, and the server's `reconnect` notification on shutdown.
- Lives in: `packages/trpc/src/interop/` (`handler.ts`, `jsonl.ts`, `socket.ts`, `errors.ts`), `src/server/handler/body.ts` (shared body reading), `src/server/subscriptions/tracked.ts`, `src/internal/effects.ts` (`interruptSignal`), `src/transformer/progressive-json/stream.ts` (`sourceOf`), `packages/trpc/src/interop/handler/handler.test.ts` (real `@trpc/client` 11 links over a Node server), `src/interop/handler/socket.test.ts` (a socket still connecting at `dispose()`), `www/docs/migrations/from-v11.md`.

## Types package, shutdown notice and WebSocket batch cap (agent)

- The question (first-release review, 2026-10-19, question 13): "Interop: ship `V11AppRouter` in a package? Recommended: no, keep it a docs recipe so `@trpc12/trpc` takes no dependency on `@trpc/server` 11. A `drain()` that sends v11's reconnect notice? Recommended: no, the 1012 close already makes clients reconnect, and v11's notice resends pending mutations. WebSocket array batches have no cap in either handler (HTTP has `batch.maxItems`). Recommended: cap both at the HTTP batch cap with `PAYLOAD_TOO_LARGE`."
- Human, 2026-10-19 (first-release review, question 13): "i don't know what this means - make a call and defer".
- Deferred: the human asked the agent to decide; revisit before 1.0.
- (agent) In plain words: old apps built for tRPC v11 can keep talking to a new v12 server through a compatibility handler. Three loose ends were left. First, the helper type that lets old apps see the new server's API stays a snippet in the docs that you copy, so the main package doesn't have to depend on the old tRPC. Second, when the server shuts down it just closes connections, which old clients already handle by reconnecting; we don't send v11's "please reconnect" message, because old clients answer it by repeating unfinished requests, which could run a payment twice. Third, an old client could pack any number of calls into one WebSocket message; now one message may hold at most as many calls as an HTTP batch (100 by default), and a bigger one is refused without running any of them.
- (agent) `V11AppRouter` stays the recipe in `www/samples/docs/src/v11-app-router.ts` and `serve-v11-clients.md#typing-v11-clients-from-the-new-router`; no export, no `@trpc/server` 11 dependency, peer or otherwise. No `drain()` on `createV11Handler`: `dispose()` and `serve()` release keep closing v11 sockets with 1012, without `stopped` results.
- (agent) Cap: `createV11Handler`'s socket refuses a message whose array holds more than `batch.maxItems` calls (100 by default, and still 100 with `batch: false`, since `wsLink` sends arrays whatever the HTTP setting). None of its calls run. It answers as v11 answers an HTTP batch over `maxBatchSize`: `BAD_REQUEST`, "Batch call exceeds maximum size", v11's error shape without a path, sent for each request in the array by id (with its `jsonrpc`) so `wsLink` settles them, or once with id null when none has an id; `onError` runs once. Not `PAYLOAD_TOO_LARGE`: v11 has a cap only over HTTP, and that's its answer there. The parity suite compares the socket's error with what `@trpc/server` 11's `fetchRequestHandler({ maxBatchSize })` sends, and lists the over-cap message as a divergence from v11's socket, which runs it.
- (agent) The v12 socket protocol has no array batches to cap: each message is one record, and an array is answered with one `PARSE_ERROR` "Invalid message" (id null), none of its calls run. A test pins it. Message size stays the platform's limit (`ws` 100 MiB, Bun 16 MiB).
- (agent) Why: the types recipe is one file users paste once, and its imports make the v11 dependency the app's. The reconnect notice risks running mutations twice for no gain over the close. An uncapped array let one message start thousands of calls, each with its own `createContext`, where an HTTP request stops at `batch.maxItems`.
- (agent) Lost: `V11AppRouter` isn't versioned with the handler, so a change to `TRPCBuiltRouter` needs the recipe updated by hand; old clients don't learn that a shutdown is coming before the close; a v11 app that sends more than 100 calls in one tick over `wsLink` gets errors where v11 ran them (`batch: { maxItems }` raises the cap).
- (agent) Open: a separate socket cap option if apps need one apart from HTTP; an `experimental_drain()` that waits for calls in flight before the close; a v12 socket batch message, if one is ever added, takes the same cap.
- Lives in: `packages/trpc/src/interop/handler/socket.ts` (`tooLarge`), `handler.ts` (`maxSocketBatch`), `errors.ts` (`BATCH_TOO_LARGE`); tests in `socket.test.ts`, `v11-parity.test.ts` and `packages/trpc/src/server/sockets/websockets.test.ts`; docs in `www/docs/migrations/from-v11/serve-v11-clients.md`.
