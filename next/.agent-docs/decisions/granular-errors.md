# Granular errors in the core, a few categories at the call site (human)

- Human, 2026-10-18: "`Effect.Effect<XXXX, AnyTrpcError>` in general is a bad practice isn't it? shouldn't we be more specific about which trpc error it is? we could tag them all couldn't we?"
- Human, 2026-10-18 (how far to narrow): "i'd like to push it as far as possible without it becoming annoying and handling dozens of type of errors for every rpc call, even when you haven't declared an input
  it'd be good to have some generic errors that you'd be forced to match (or sub-types) but at the core we should be as granular as possible even if some errors won't reach a standard client call"
- Human, 2026-10-18 (TanStack Query): "would it be possible to make it automatic said errors to `useQuery()` - e.g. that `.queryOptions()` would inform useQuery() which errors are actually possible?"
- (agent) The core is granular: every built-in code has a class, `TrpcError.NotFound`, `TrpcError.PayloadTooLarge`, … (25, like Effect's `HttpApiError.NotFound`), named from their codes at load. Each is a `TrpcError<Code, undefined>`, `defined: false` until a resolver returns it, with `_tag` its code ([`error-tags.md`](./error-tags.md) stands). tRPC's server code builds its errors with them; client code writes `new TrpcError({ code })`, whose code strings the bundle already has (the classes would grow the core client bundle, which is over its size target). Functions that make or forward a known set of errors type their channel with exactly those classes (`Effect<Uint8Array, PayloadTooLarge | BadRequest>`).
- (agent) `AnyTrpcError` stays only where a channel carries some procedure's errors that the code can't know (the handler core, `callProcedure`, a link's `OperationStream`) and on observers that see every error (`onError`, `loggerLink`, `retryLink`'s `delay`). Helpers that add errors to a procedure name them: `experimental_durable()` fails with `Conflict | BadRequest` and `ConnectionToken.verify` with `Unauthorized`, not `TrpcError` (which had reopened the client's union to `TrpcError<string, unknown>`), and a replayed failure is the procedure's own error.
- (agent) At the call site, built-in errors fall into four categories, which `matchError()` made you handle (or `builtin` for all four) until [exhaustive-match-error](./exhaustive-match-error.md) replaced both with required link-code keys and one `unexpected`; `ERROR_CATEGORY` keeps them:
  - `rejected`: the server refused the call. A thrown built-in 4xx code (`UNAUTHORIZED`, `NOT_FOUND` for a missing procedure, `BAD_REQUEST`), a protocol mismatch (`PARSE_ERROR`, `METHOD_NOT_SUPPORTED`, `PAYLOAD_TOO_LARGE`, …), and `CLIENT_ERROR`.
  - `unavailable`: no usable answer; trying later may work. `NETWORK_ERROR`, `BAD_RESPONSE`, `STREAM_INTERRUPTED`, `TIMEOUT`, `TOO_MANY_REQUESTS`, `BAD_GATEWAY`, `SERVICE_UNAVAILABLE`, `GATEWAY_TIMEOUT`.
  - `failed`: the server broke (`INTERNAL_SERVER_ERROR`, masked in production, and `NOT_IMPLEMENTED`).
  - `aborted`: the call's `signal` stopped it (`CLIENT_CLOSED_REQUEST`).
- (agent) A category handler's `e.code` narrows to that category's codes (the "sub-types"); `ERROR_CATEGORY` maps each built-in code to its category. The defined part is unchanged: a procedure's own codes, and its input's `BAD_REQUEST` only when it has an `.input()`.
- (agent) TanStack Query already carries each procedure's `ClientError` as `TError`: `queryOptions()`, `infiniteQueryOptions()`, `mutationOptions()`, `subscriptionOptions()` and the query key's `DataTag`, so `useQuery(trpc.x.queryOptions())`, `useQueries`, `useInfiniteQuery`, `useMutation` and `useSubscription` infer it, transport and abort errors included. Where TanStack can't carry it: `Register.defaultError` types only what has no options (`QueryCache` and `MutationCache` callbacks); `useSuspenseQuery` and `throwOnError` throw to an error boundary, which gets React's untyped error (narrow with `isTrpcError`); a `select` that throws puts a non-tRPC error in `error`, so `select` must not throw.
- Why: an error type should list what can actually happen, so `catchTag` and `matchError` find the cases; and a call site shouldn't have to name 25 codes it can do nothing different about.
- Lost: `BuiltinError` is still one member per code (so `switch (err.code)` works), but `matchError()`'s `builtin` now competes with category keys; code that matched `builtin` keeps working.
- Open: a client-side `TIMEOUT` (proposal 24 Q24.6 B) would join `unavailable`. Granular reasons inside one code (a missing procedure vs a thrown `NOT_FOUND`) stay a `message` and a `cause`; a second discriminator would need a human's call against `error-tags.md`.
- Open (human): should tRPC's own errors also carry a tagged `reason` inside their code? [#7677](https://github.com/trpc/trpc/pull/7677) built one before the classes above landed, for the same ask ("We should probably be more specific with trpc errors too so we just don't use a blanket one everywhere"): Effect's `HttpServerError`/`AiError` shape, a closed `Data.TaggedEnum` of about 60 failures (`BodyTooLarge { limit }`, `ProcedureNotFound { path }`, `FetchFailed`, `SerializerMismatch { server, client, transport }`, …) on an optional, never-serialized `TrpcError.reason`, with one table fixing each reason's code and message. It wasn't ported to `v12`, since the files it touched have been rewritten since and the classes answer most of it; its commit is `d2e1cbbbd`.
- Lives in: `packages/trpc/src/internal/error.ts` (`TrpcError.<Code>`, `ERROR_CATEGORY`), `src/client/client.ts` (`matchError`), `src/middleware/durable.ts` and `src/cloudflare/token.ts` (the helpers' own codes); tested in `src/server/errors.test.ts`, `src/middleware/durable.test.ts`, `packages/tanstack-react-query/src/index.test.tsx` (each hook's `error`); documented in `docs/client/errors.md`, `docs/server/errors.md`, `docs/integrations/tanstack-query.md#errors`.
