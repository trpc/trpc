# The client's error union is closed, with `matchError()` (human asked)

- Human, 2026-10-18: "i feel like these sort of examples are a bit unintuitive […] because it's still `| undefined` in the else if", "there's also probably more errors that can be inferred rather than "unexpected error" and it could just be an always-defined one and there's probably sub-types of it that can be inferred further", "people can use switch cases and stuff", and "use your judgement and feel free to redesign the api to be more fool proof to error handling and clearer in the docs".
- (agent) Proposal 24's recommended picks, without its shells:
  - Q24.1 A: the server masks thrown, undeclared `TrpcError`s with a custom code as `INTERNAL_SERVER_ERROR` (exposed like other unexpected errors), with the original sent to `onError`. Since [thrown-errors-and-exhaustive-declarations](./thrown-errors-and-exhaustive-declarations.md), only from a procedure with `.errors()`; without them the code and `data` reach the client as an `UndeclaredError`.
  - Q24.2 A: the client's `defined: false` part is `BuiltinError`, one member per built-in code (`TrpcError<C, undefined> & { defined: false }`), replacing `UnexpectedError`. So `switch (err.code)` narrows the whole error, and `Exclude<E, { code: 'NETWORK_ERROR' }>` removes one.
  - Q24.3 A: `matchError(err, handlers)` in `@trpc12/trpc/client`. Every defined code's handler is required, and so is `builtin` while built-in errors are left. Extra keys are type errors. A built-in error with a defined code (the server lacks the procedure) goes to `builtin`, and one with a code the types don't know rethrows when nothing handles it. Since [exhaustive-match-error](./exhaustive-match-error.md), `builtin` is `unexpected`, and link codes are required keys too.
  - Q24.6 A, in part: a response the client can't read (not tRPC's, undecodable, or failing `experimental_validationLink`'s check) is the new client-side `BAD_RESPONSE`, with status 0. It isn't retried as a server failure. The server still sends `PARSE_ERROR` for requests it can't parse.
- (agent) Built-in errors never have `data`. An undeclared thrown error with a built-in code keeps its code and loses its `data` on the server, and every client-side path (wire decoding, links, OpenAPI and v11 interop) folds an undefined error the same way, through `toUntypedError`. Custom codes from links become `CLIENT_ERROR`; from the wire, they stay as they are. `runLinks` applies it once at the top of the chain, so the types match what arrives.
- (agent) `experimental_validationLink`'s output mismatch keeps its issues on `cause.issues`, not `data`.
- (agent) `safe()` rethrows framework control flow (errors with a `digest`, like Next's `redirect()`), as the in-process links already do.
- (agent) The docs lead with "check `error` first", since destructured tuples narrow once the error is handled. The home page and getting-started use `matchError`.
- Why: with `code: string` and `data: unknown` in the open part, nothing told callers what was left to handle, and checking `data` instead of `error` left `| undefined` behind. Closing the union makes the error type a list of every way a call fails.
- Lost:
  - Thrown errors' `data` no longer reaches the client with a built-in code. Declare or return them to keep it.
  - v11 interop errors' `data` moves to `cause.data`.
  - `experimental_validationLink` mismatches lose `data.issues`.
- Open: shells (Q24.4, Q24.5), a client `TIMEOUT` (Q24.6 B), stale clients (Q24.7) and checking error `data` on the client (Q24.8), in [error-ownership](./error-ownership.md).
- Lives in: `packages/trpc/src/internal/error.ts` (`BAD_RESPONSE`, `isBuiltinCode`, `toUntypedError`), `src/server/execution/execute.ts` (`normalizeCause`), `src/client/types.ts` (`BuiltinError`, `ClientError`), `src/client/client.ts` (`matchError`, `safe`), `src/client/link.ts` (`runLinks`), `src/client/links/{events,http,socket,validation}.ts`, `src/openapi/{errors,link}.ts`, `src/interop/link.ts`; tested in `src/server/errors.test.ts`, `src/client/links/links.test.ts` and `http-edges.test.ts`; documented in `www/docs/client/errors.md` and `www/docs/server/errors.md`; spikes in `spikes/closed-errors/`.
