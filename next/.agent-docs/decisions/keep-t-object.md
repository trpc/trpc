# Keep `t`; standalone plugin packages work through `.concat()` (human)

- Human, 2026-10-10 (Q3.5): "let's keep `t`, but we need to make sure that we can still make some sort of plugins of standalone packages... what we now have in `.concat()` where a plugin can have a requirement of a specific thing or add it etc".
- Requirement: a package publishes a builder fragment from its own `initTrpc<{ ctx; meta }>()`, which is its requirement, and the app composes it with `authed.concat(plugin)`: requirements are checked against the current ctx (errors name the missing key), contributions flow on, and the published `.d.ts` is readable ([notes/concat-plugins.md](../notes/concat-plugins.md)). This must keep working as the builder grows; `.concat()` merges declared errors and services with the same checks.
- Why: `t` keeps the root types in one place and is what v11 users know. Top-level imports would need oRPC's bottom-up context model.
- Rejected: top-level imports only, or both forms.
- (agent, Effect-native first) A standalone middleware (`middleware<{ ctx }>()`, `middleware.effect`) that needs ctx keys the procedure lacks adds them to the procedure's root ctx, like an Effect requirement moving outward: `createContext` and in-process callers must supply them (oRPC's model). A key the procedure has with an incompatible type stays a type error (`NeedsCheck`), so `string | null` can't silently become `string`. `.concat()` keeps the strict check the human chose above; a plugin wanting the loose form exports a middleware instead. Lost: v11's "missing ctx is a type error at `.use()`"; the error now shows up where ctx is created.
- (agent) Since the composition answer in [`root-extensions.md`](./root-extensions.md), root extensions use the same method: `t.concat(ext)`.
- Lives in: `packages/trpc/src/server/procedures/builder.ts` (`NeedsCheck`, `WithNeeds`); `tooling/portability` publishes a plugin builder; `packages/trpc/src/server/procedures/composition.test.ts`; docs in `docs/server/middleware.md`.
