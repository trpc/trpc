# WebSocket upgrades and sessions run on Effect's `Socket` (human asked)

- Human, 2026-10-18: some code isn't "Effect-like", the WebSocket upgrade code for one; use the Effect-native APIs. The outcome (sessions on Effect's own socket APIs) is theirs; the details below are the agent's.
- Human, 2026-10-18, later: also move the socket calls onto fibers in a `FiberMap`, and take the MessagePort server side off callbacks.
- (agent) An upgrade (`request.upgrade`, the `ws` server on Node and Bun's own, under `serve()`, `toHttpEffect()` or `handler.routes`) hands Effect's `Socket` straight to the socket core. Before, `server/sockets/upgrade.ts` rebuilt a `WebSocket`-shaped event emitter around that `Socket`, and the core wrapped it in callbacks again.
- (agent) `handler.websocket(ws, { request })` (Deno, Workers without hibernation) turns `ws` into a `Socket` with Effect's `Socket.fromWebSocket` and runs the same session, so one implementation serves every WebSocket. A socket handed over while still connecting (Deno's) gets its writes once it opens, where they used to be dropped.
- (agent) One runner, `runSocket` in `server/sockets/socket-session.ts`: the socket's frames are a `Stream` from its reader, writes go through one bounded `Queue` to its writer (which waits for a slow client, see below), the idle timeout is a `FiberHandle` timer that each frame restarts, and the session's `Scope` cleans up. No `setTimeout`, no listener bookkeeping. On idle it sends the 1001 close and stops the calls without waiting for the peer to answer, as before.
- (agent) Raw TCP sockets (`experimental_serveSocket()` from `@trpc12/trpc/socket`) and the v11 handler's `wsLink` sessions use the runner too. The v11 handler registers its socket server the way `createFetchHandler()` does, so under `serve()` its upgrades get Effect's request like v12's instead of a web `Request` copy. Its calls run in a `FiberMap` in the session's scope instead of a hand-made `Scope.makeUnsafe()`, and an idle timeout now stops them at once.
- (agent) `connectionReceiver` (the v12 socket protocol, behind every transport) is an Effect in the connection's `Scope`: `receive(message)` and `close` are Effects, and each request's call is a fiber in a `FiberMap` keyed by its id. An `abort` is `FiberMap.remove`, the connection's close is `FiberMap.clear`, and the end of the scope interrupts whatever is left. The call itself is one `Effect.gen` (procedure lookup, `createContext`, the run, its events or deferred chunks) instead of an `async` function with `live()` checks: an interrupted fiber sends nothing more. It calls the handler core's `makeContext` and `run` in its own fiber ([`handler-core-on-effect.md`](./handler-core-on-effect.md)). Its `AbortSignal`, shared by `createContext` and the procedure, aborts when the fiber is interrupted, as the `AbortController` did on abort and close; the v11 session's calls now abort theirs the same way, where before it only aborted while `createContext` or the run was pending.
- (agent) MessagePorts: `serveMessagePort` reads the port's messages as a `Stream` (a queue the `message` listener feeds, ended by `close`) and runs the receiver over it, and `handler.messagePort()` forks that with `Effect.runFork`. The listeners attach when `messagePort()` is called, not when the fiber gets to them: a forked fiber can start after the port's next message, and ports without a listener drop it. `Connection` lost `onMessage` and `onClose`; it is only where server messages go.
- (agent) The v11 session's `frame` and `close` are Effects too, so `subscription.stop` and a closed socket are `FiberMap.remove` and `FiberMap.clear` in the session's fiber instead of `Effect.runFork` calls, and its calls fork with `FiberMap.run` instead of a captured runtime.
- (agent) `WebSocketLike` gains `removeEventListener`, which `Socket.fromWebSocket` needs. Every standard `WebSocket` has it; a hand-rolled object needs it now, which is fine before release ([`no-backwards-compatibility-yet.md`](./no-backwards-compatibility-yet.md)).
- (agent) `experimental_durableLocker`'s client socket to the lock object is Effect's `Socket` too (`Socket.fromWebSocket` over the accepted `response.webSocket`): waiting for the lock is one `pull` of its reader under `Effect.timeoutOption`, a close or error before it dies with "The lock object closed the socket" as before, and releasing or expiring writes a `CloseEvent`. Before, it was a `Deferred.makeUnsafe` resolved by `addEventListener` callbacks. `DurableLockSocket` is `Socket.WebSocketLike` plus `accept()`, so a hand-rolled one needs `removeEventListener` and `send` and gets each listener's event; Workers' `WebSocket` has them.
- (agent) The client's links connect as scoped Effects, and a connection's server messages are a `Stream`. `wsLink` builds Effect's `Socket.fromWebSocket` over the `WebSocket` it constructs, and connecting acquires that socket's reader: it dials and waits for `open`, with no timeout, as before, since a socket that never opens gets a close event. Writes go through one `Queue` to the socket's writer, and the connection's `RcRef` scope closes it. `experimental_socketLink` uses the same connection code. Its socket used to live in a scope of its own that nothing closed. A connection is lost when its messages end on their own; releasing it interrupts the stream instead. Before, `wsLink` was a `new Promise` over `addEventListener`, with callbacks for messages and close.
- (agent) `experimental_messagePortLink` adds the port's listeners once, since `MessagePortLike` can't remove them, and they publish to a `PubSub`. Each connection subscribes before it sends anything, and its messages are that subscription as a `Stream`, ended by `close()` or the port's `close`. A closed port now fails calls with `NETWORK_ERROR`; before, a connection opened after the port closed left its calls hanging.
- (agent) Kept off the native APIs:
  - `serveAsWebSocket` in `server/sockets/upgrade.ts`: a handler that isn't ours, passed to `toHttpEffect()` as `FetchLike & WebSocketHandlerLike`, still gets a `WebSocket`-shaped object. Its `websocket()` contract is the WHATWG interface, and Effect only adapts the other way. The adapter runs on `runSocket` too.
  - Cloudflare hibernation: Workers deliver frames as Durable Object method calls and may evict the object between them, so no long-lived fiber can read a `Socket`. Effect also has no Cloudflare platform package. The adapter keeps each socket's receiver in a `Scope.makeUnsafe()` scope, runs each message's `receive` with `Effect.runFork` (it starts synchronously, so messages are handled in order) and closes the scope in `webSocketClose`.
  - MessagePorts: Effect has no `Socket` over `postMessage`, so they get the receiver over a message `Stream` rather than `runSocket`, and `experimental_messagePortLink` isn't a `Socket` either.
  - `wsLink` still drops a write once its socket is closing (`readyState` past 1): Effect's writer would call `send` anyway, and a closing socket may throw on it (Deno's does).
- Why: Effect already ships both adapters needed (upgrade to `Socket`, `WebSocket` to `Socket`), so ours duplicated them. One runner gives every transport the same interruption, cleanup and idle handling.
- Lost: `handler.websocket` depends on `Socket.fromWebSocket`'s behaviour: a 10 s wait for `open`, and it sets `binaryType = 'arraybuffer'` on the socket. Also, `@trpc12/trpc/http` reaches our own handlers through the handler's `UpgradeServer` service ([`handler-services-in-effect-context.md`](./handler-services-in-effect-context.md)) rather than through their public `websocket()`. A MessagePort's messages reach the receiver through a queue, so each is handled a scheduler turn after its event rather than in the listener.
