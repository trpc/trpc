# Transformers are replaceable: none, sync or streaming, and named transformers as in v11 (human)

- Human, 2026-10-15 (decisions round 3, Q19 = proposal 11 Q11.4/Q11.5): "Let's do B. Some people may not want a serializer at all. It makes it tricky though as we can see in the trpc code, but that's okay. So we should have options for sync transformers like superjson/devalue and async ones like danson thay can do anything and make sure thay we have that json transform of types when there isn't a standard one. We may not even go with danson as our default and do something else before we do final release of this version, we're still pre beta".
- Human, 2026-10-21: "also we called those transformers in v11, let's keep that name for consistency". What v12 called a serializer is a transformer, as in v11's `transformer: superjson`. Renamed without aliases, since nothing has shipped:
  - `Serializer` to `Transformer`, `AnySerializer` to `AnyTransformer`, `FormOfSerializer` to `FormOfTransformer`, the handlers' `SerializerOption` to `TransformerOption`.
  - `jsonSerializer` to `jsonTransformer`, `createSyncSerializer` to `createSyncTransformer` (`SyncSerializerOptions` to `SyncTransformerOptions`), and danSON's `createSerializer` to `experimental_createTransformer` (`SerializerOptions` to `TransformerOptions`), experimental by the same day's answer in [`serializer.md`](./serializer.md).
  - The `serializer` option to `transformer` on `createFetchHandler` and every handler, every link, `localLink` (`transformer: false`), `hydrationOptions` and `experimental_durable`; `getClientSerializer` to `getClientTransformer`; `@trpc12/experimental-react-atom`'s `serializerSchema` to `transformerSchema`.
  - The `@trpc12/trpc/serializer` entry point to `@trpc12/trpc/transformer`, in `src/transformer/`; the `SerializerMismatch` tag to `TransformerMismatch` (made by the link, never sent by a server, so no wire change).
  - The Serializers page to Transformers, at `server/transformers`; `/v12/docs/server/serializers` and its `.md` redirect there (`movedPages` in `www/build/old-routes.ts`).
  - (agent) The codemod keeps a v11 link's `transformer` key and wraps its value: `transformer: createSyncTransformer(superjson)`. v12's option takes a `Transformer`, not superjson itself; `createV11Handler({ transformer: superjson })`, which serves old clients, still takes v11's.
  - (agent) danSON's internals keep "serializers" for its per-type functions (`SerializeRecord`, `stdSerializers`), which aren't transformers, and this file and [`serializer.md`](./serializer.md) keep their names so their links and pages don't move.
- Human, 2026-10-21: "1. Rename. We don't care about breaking changes before v12 2. Yes 3. With and without 4. Progressive json". Its 1 answers whether the wire keeps the old names: it doesn't. The response header is `trpc-transformer` (`HEADER.transformer`; it was `trpc-serializer`), and the socket `init` message carries `transformer` both ways (it was `serializer`). No alias reads the old names: a client and a server from either side of the rename don't see each other's mismatches, and nothing has shipped. v11's wire, which `createV11Handler` and the v11 link speak, has neither and is unchanged.
- The RPC transformer can be replaced wholesale. Three kinds:
  - **None**: plain `JSON`.
  - **Sync**: whole values in and out (superjson, devalue).
  - **Streaming**: handles deferred values, streams and files itself (danSON).
- Client types follow the serializer. Without one that keeps a type (plain JSON, or a type superjson doesn't know), the client sees the JSON form of the output (`Date` → `string`, `Map` → `{}`, `undefined` keys dropped), like v11's `inferTransformedProcedureOutput`.
- danSON as the default is provisional; the default may change before the final release (still pre-beta). Supersedes the "extend only" reading of [`serializer.md`](./serializer.md).
- (agent) With a sync serializer or none, the transport frames streams: JSONL chunks and SSE events each carry one serialized value, as v11 does. Nested promises and iterables, and `File`/`Blob` outputs nested in other values, need a streaming serializer; root `File`/`Blob` outputs still work as raw responses on unbatched HTTP ([`files.md`](./files.md)).
- (agent) Readable GET params (`?id=1&tags[]=a`) are the streaming default's encoding; other serializers use `?input=<serialized JSON>`. Superseded by Q11.3 below ([`serializer.md`](./serializer.md)): every serializer uses `?input=`.
- Why: some apps want no transformer, or one they already use; the type transform keeps clients honest when types don't survive. "Transformer" is v11's word for the same option, so v11 users and the codemod keep one name.
- Lost: one format with guaranteed native types everywhere; more transport code (two framing paths, as v11 has). With the rename, v11's `transformer: superjson` reads as if it should work as is; it's a type error, and the docs and codemod wrap it.
- (agent) Built with the Open's lean (CT-C), pending a decision: `initTrpc<{ serializer: typeof s }>()` puts the serializer's output form on every procedure; client types use it, `createFetchHandler` and `createTrpcRsc` require that serializer, and in-process callers keep native types. `Transformer<TForm>` carries the form as a phantom `'~form'`; `createSyncTransformer<TKeeps>(transformer)` and `jsonTransformer` implement the same `Transformer` interface as danSON (`kind: 'sync' | 'none'`), so the transport keeps one code path: they frame only a root deferred value (head `{ root }`, then `[0, status, value]` chunks).
- (agent) Error `data` types don't follow the form yet.
- (agent) Now they do: a defined error's `data` arrives in the result form, as outputs (`ErrorData<D, F>`; `{ at: Date }` is `{ at: string }` under `jsonTransformer`), since the handler serializes errors with the endpoint's serializer. Errors a link declares keep their types: the link makes them on the client.
- Human, 2026-10-16 (Q11.5, decision round): "It should live in the http handler, it's fine if it doesn't give type errors when missing declaration in http links, maybe we can do runtime errors for that". The serializer is set on the HTTP handler and on the link, not on `initTrpc`. Client types follow the link's serializer; a link without one types results as plain JSON. A mismatch isn't a type error: the handler names its serializer in a `trpc-serializer` header (`trpc-transformer` since 2026-10-21), and the link fails with an error saying which serializer to pass.
- Human, 2026-10-16 (Q11.1, decision round): "B". Plain JSON is the default serializer; danSON is opt-in ([`serializer.md`](./serializer.md)). The interface stays one `Transformer` with `kind: 'streaming' | 'sync' | 'none'`.
- (agent) Built, 2026-10-16, reading the answer as "the endpoint and the link own the serializer": `initTrpc` takes no `serializer` and procedures carry no form (supersedes the CT-C bullet above). Each link declares `{ form }` from its own `serializer` option (`FormOfOptions`), and the client's first link with a form types the results ([`links-declare-result-form.md`](./links-declare-result-form.md)). `httpLink` reads the `trpc-transformer` header (`trpc-serializer` until 2026-10-21) on every response and fails with `UNSUPPORTED_PROTOCOL` when it isn't its own serializer's `name`; the message names both.
- (agent) A root `File`/`Blob` output stays the response body with any serializer; under a serializer that doesn't stream files, a batching chain types such calls as needing `{ batch: false }`, as it does for `Response` outputs.
- (agent) Socket links check too, 2026-10-16: the client's `init` carries its serializer's `name`, and the server answers every `init` with `{ type: 'init', transformer }` in plain JSON (a connection error would be in the server's format, which the client can't read on a mismatch). On another name the server runs none of that connection's calls, and the link fails them, and later calls on the connection, with `UNSUPPORTED_PROTOCOL` naming both. A client that names no serializer is served as before.
- (agent) TanStack contexts infer it, 2026-10-16: `createTrpcContext<typeof makeClient>()` (or a client type) takes the router, the links' context and their types (form included) from a client type, in all seven adapters (`SourceRouter`, `SourceContext`, `SourceLinks` in `@trpc12/tanstack-query`). `TrpcClient` records them under a phantom symbol-keyed method that `ClientTypes<T>` reads; a method so assignability between clients is unchanged, though two clients of different but equivalent routers are no longer the _same_ type. A router type with `TContext` and `TLinks` spelled out still works. Cost, measured on a generated 1,000-procedure router and a client calling each one: 834,897 instantiations against 832,482 without the key (+0.3%), check time unchanged at about 0.7 s.
