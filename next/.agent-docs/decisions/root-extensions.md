# Root extensions via `t.with(ext)` ship in v1 (human)

- Human, 2026-10-15 (decisions round 3, Q12 = proposal 03 Q3.6): "A".
- `initTrpc<{ ctx: Ctx }>().with(ext)` adds what an extension brings from values: meta keys, ctx, error codes and Effect services. Extensions chain: `.with(openapi()).with(rateLimit({ per: 'user' }))`.
- (agent) Values go through `.with()` rather than `initTrpc<{…}>()` because TypeScript has no partial type-argument inference: the caller's `ctx` type argument and the extension's inferred types can't share one call.
- (agent) An extension is plain data plus types (meta schema, ctx additions, error codes, a `Layer` for its services), not a plugin hook into the protocol ([`plugins-are-effect-middleware.md`](./plugins-are-effect-middleware.md)). Call-level behaviour it needs goes through root middleware.
- Why: packages like rate limiting or auth can add typed meta, ctx and errors without each app restating them.
- Lost: a smaller v1 surface; extension typing must be kept stable once published.
- (agent) Spiked and built: an extension is a procedure builder from the package's own `initTrpc` (its root ctx = what it needs, its meta type = keys it adds, its default meta = defaults under the app's). `t.with(ext)` is `.concat()` lifted to the root, plus merged meta; it answers the `.concat()` part of the Open. Chained inference holds across `.with().with()`; `WithCheck` rejects missing ctx and meta keys declared with another type. Error codes merge as unions, as with `.concat()`.
- (agent) No `layer` field: an extension provides services per call with `.provide()` (or Effect middleware); services it only uses stay in the handler's `layer`. A shared `Layer` would need the handler to merge extension layers; left for when a package needs it. Whether `.route()` becomes an extension: answered below.
- Human, 2026-10-16 (decision round): "B. Also rpc handler should be the same... I think our work on a generic builder should help here?". OpenAPI's `.route()` moves out of the core builder into an `openapi()` extension, and the RPC protocol is an extension the same way: the core builder knows no protocol, and each protocol's handler reads its own slot of the builder's options bag (proposal 03's single `TDef` generic).
  - (agent) Built, 2026-10-16, as the answer's option B was worded ("the core and generators have to find the extension's meta by its key"): `openapi()` from `@trpc12/trpc/openapi` is a root extension that adds the `route` meta key, `t.procedure.meta({ route: { method: 'GET', path: '/posts/{id}' } })`. `.route()` is gone from the procedure and contract builders, and `route` from their internals. The OpenAPI handler, generator, `toContract`, `generateContractFromOpenApi` output and `@trpc12/nest` read `meta.route` through `routeOf(def)`.
  - (agent) For `route` to keep merging key by key with composed `spec` functions ([`route-spec-override.md`](./route-spec-override.md)), roots and extensions declare per-key meta merges: `initTrpc({ mergeMeta: { key: (before, next) => merged } })`. `.with()` carries them into the app's root, and `t.implement()` merges a contract's meta over the root's through them.
  - (agent) Contracts take extensions for their meta: `contract.create().with(openapi())` adds the meta keys, merges and default meta, and throws if the extension has middleware or inputs. Implementing a contract that uses `route` needs a root with `openapi()` too (the existing meta check).
  - (agent) `.meta()` now rejects keys the root doesn't declare (`UndeclaredMeta`), so `.meta({ route })` without `.with(openapi())` is a type error rather than a silently unmerged key.
  - (agent, tentative) The RPC half: after this, the core builder holds no protocol state, and the RPC handler reads no per-procedure slot, so there is no `rpc()` extension to add yet. It gets one when RPC grows per-procedure options (a cacheable `GET` mutation, say). `t.router({ prefix, tags }, …)` OpenAPI groups are still core, on routers rather than the builder.
  - Lost: `.route()` as a method (`.meta({ route: … })` is longer); `.concat()` carrying a plugin's route (it carries steps and errors; meta goes through `.with()`); the `openapi` name for a local handler variable next to the import.
- Open (human): root-declared meta versus oRPC v2's meta plugins. oRPC v2 removed `.$meta<T>()` (one meta type declared up front) in favour of `defineMeta(name, merge)`, which returns `[metaPlugin, getMeta]`. Any module defines a key and its merge, sets it with `.meta(cacheMeta(true))` and reads it with `getCacheMeta(procedure)`, with nothing declared at the root. A hand-written `MetaPlugin` can also infer from or restrict the procedure's input, output and errors. Ours declares every key at the root (`initTrpc<{ meta }>()`, or `.with(openapi())`), `.meta()` rejects undeclared keys (`UndeclaredMeta`), and merges are `mergeMeta` per key. Options: A) keep root-declared meta, so resolvers and middleware see one typed `meta`; B) meta plugins (`.meta(route({ … }))`), so an extension that only adds meta needs no `.with()`, at the cost of the typed `meta` object in resolvers ([`meta-in-resolvers.md`](./meta-in-resolvers.md)); C) both: plugins for packages, root `meta` for the app. Source: `.repos/orpc/apps/content/docs/metadata.mdx`, `.repos/orpc/packages/contract/src/meta-utils.ts`.
