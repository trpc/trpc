# WebSocket reconnect switches over make-before-break (human asked)

- Human, 2026-11-05, relayed: "don't stop talking to the old socket until the new socket is established. All new requests (queries, mutations, new subscriptions) keep going on the old socket until the successor is open and connectionParams have resolved", "Don't unsubscribe the old subscription until the new one is established", "If the successor fails, keep the old one serving", and, matching v11's #7925: "The successor's first frame for a subscription (data, started, error or stopped) means it's established", "Dedupe the old socket's overlap events by id when the successor replays them, instead of buffering", "If the old socket dies mid-move, keep the sub on the successor with no second `started`", "Untracked subs are at-least-once during the overlap."
- Human, 2026-11-05, relayed (D5, as #7727 and #7925 now do): "while the old socket still serves, never show `connecting`, even after repeated failed successor attempts. Keep retrying with backoff, and surface the last replacement error only when the old socket ends. Drop any 3-failure threshold."
- Human, 2026-11-05, relayed (as #7925 now does): "after a move, a subscription without a lastEventId keeps delivering the old leg's events until the old leg confirms the stop, or is lost. No timeout. Tracked subscriptions are unchanged (dedupe by id)", and "Make the server send `done` (or an equivalent ack) after an abort."
- (agent) v12's `wsLink` has no connection state, so nothing shows `connecting`. Successor failures don't count toward a subscription's `reconnect.attempts`. When the old connection ends, its subscriptions reconnect as after any drop, and one that runs out of attempts fails with `NETWORK_ERROR` whose cause is the last error.
- (agent) The server sends `{ id, type: 'started' }` once a subscription's resolver has run, before its first event, so a subscription that publishes nothing still confirms a move. `wsLink` doesn't show it to subscribers.
- (agent) On `reconnect`, `wsLink` keeps the old connection as the shared one while a successor opens in its own scope; the successor only becomes the shared connection once its `connectionParams` resolved and `init` was sent. A successor that fails to open is retried with the link's `reconnect.delay`, for as long as the old connection lasts.
- (agent) Each moving subscription then subscribes on the successor with its last delivered `lastEventId`, and the old leg keeps delivering. The successor's first message promotes it: the old leg is aborted (its outbox is flushed before the socket closes) and its later messages dropped. Each leg decodes its deferred values with its own decoder, closed when the leg ends, so the successor's numbering never meets the old leg's. While the successor resends, an event whose id the old leg delivered during the overlap is dropped once; the first event with a new id ends the dedupe.
- (agent) A subscription sent to the successor without a `lastEventId` (it has delivered no tracked event) can't be resent what the old leg delivered before the successor's procedure listened, so an event published after the successor's `started` but before it listened was only on the old leg, and was dropped. Now the old leg is sent `abort` on the promote but stays registered: its events are delivered, possibly twice, until the server answers the abort with `done` (or `error`), or the old connection is lost. No timeout: a drain's own timeout closes the old connection. Its deferred values decode on its own decoder, beside the successor's (until 2026-11-05 they were dropped, because the call had one decoder that the move handed to the successor); a deferred value still open when the leg stops ends as a cut stream. The leg no longer counts as a subscription to move, so the supervisor finishes, but it holds the old connection open until then.
- (agent) The server answers an `abort` for a call it's running with `{ id, type: 'done' }`, once the call's fiber has stopped (`FiberMap.remove` waits for it), so nothing for that id follows. An `abort` for an id it isn't running gets nothing, as before; a hibernated subscription is unparked without one. A client that doesn't wait for it ignores a `done` for an id it no longer runs.
- Human, 2026-11-05, relayed: "consider #7727's approach: right after the stop/abort, send a ping on the old connection and end untracked delivery at its pong. … Adopt it if it's sound on v12's server."
- (agent) Not adopted. v12's Node, Bun and `MessagePort` servers handle a connection's frames one at a time (`runSocket` runs each before reading the next), and the `abort` handler sends `done` before it returns, so a pong sent after the abort always arrives after the `done`. It can't end delivery sooner. It doesn't bound a procedure that ignores the abort either: an async generator stuck in an `await` doesn't hold up the interrupt (the server sends `done` at once; checked by hand), and a resolver that blocks interruption (an uninterruptible Effect) holds the frame loop, so the pong waits with the `done`. Cloudflare's hibernating sockets handle each message on its own fiber, so a pong there can come before the abort is handled, and ending at it would drop events. A connection that never confirms is still closed by the drain timeout.
- (agent) A successor lost, or failing with a connection error, before it answers leaves the subscription on the old leg, and the supervisor tries again. An old connection lost mid-move promotes the successor leg. A successor itself retired before it answers: the subscription moves on to the one after it.
- Why: a drain is a planned shutdown with a grace period, so the client can use it to move without a gap and without the subscriber seeing a reconnect. Dedupe instead of a buffer: a buffer stalls the subscriber if the successor never answers.
- Lost: moving subscriptions at once and dropping the old connection's later events (the earlier v12 behaviour), which lost the events published while the successor opened its `connectionParams`, and left no subscription served if the successor failed. Also v11's earlier `connecting` with the last error after 3 failed successors, which showed subscribers a reconnect while the old socket still served them. Also lost: stopping an untracked subscription's old leg on the promote. Its duplicates now last until the server's `done`, and the old connection stays open that long; a server without the `done` (before this change) keeps it until the drain closes it.
- Lives in: `packages/trpc/src/client/links/socket.ts` (`retire`, `supervise`, `attach`), `src/server/sockets/socket.ts` (`started`, `done` after `abort`), `src/internal/protocol.ts`; tests in `src/client/links/socket-reconnect.test.ts` and `src/server/sockets/drain.test.ts`.
