- (agent) `next/www` owns the list: `pnpm --filter @trpc12/www sponsors:sync` (`www/build/sponsors-sync.ts`, with `SPONSORS_SYNC_GITHUB_TOKEN`, KATT's) reads KATT's and the trpc organization's sponsorships from GitHub's GraphQL API and writes `www/sponsors.json` and the sponsors section of the repo's `README.md`; `sponsors:readme` rewrites the README from `sponsors.json` without GitHub. It replaces the v11 site's `script.pull.ts` and `script.push.ts` on this branch, and `old-docs:copy` no longer copies their output.
- (agent) A sponsor's weight is what they've paid the two accounts in all (from GitHub's sponsors activity log, below), as a share of whoever paid the most (1 to 100), instead of the old guess (current tier × months since they started, a hand-kept list of yearly sponsors, minus 10% for organizations). A new sponsor GitHub hasn't charged yet counts their monthly tier. Sponsoring both accounts makes one sponsor, not two bubbles. Direct sponsors (SerpApi, invoiced yearly) and money GitHub can't attribute are `sponsorsConfig` in the script.
- Human, 2026-10-19, on Greptile's `extra` payment: "can it be deleted?" (agent) Gone: it was the v11 script's override for Greptile's three months from a private account before they sponsored as `greptileai`; Greptile now weighs what GitHub says `greptileai` paid.
- (agent) The README's tiers are the site's (below): a table per tier, by rank, avatars smaller down the tiers, then everyone else as backers by weight, avatars fetched at twice their size; an empty tier has no table. Names and links are HTML-escaped (the old script `encodeURI`'d names, so alt texts read `Dr.%20B`).
- (agent) The sync decodes every response, follows every page, skips deleted sponsors, and writes nothing when the token can't see tiers, sponsors or payments, saying whose token it needs, so a wrong token can't empty the site. The fetch goes through Effect's `HttpClient`, so the tests run it against a fake GitHub (`www/build/fake-github.ts`); the queries were checked against GitHub's live schema with a token that isn't KATT's, which can't read tiers or payments.
- (agent) `main`'s sync still writes the README's sponsors there. After a merge of `main` that changes `README.md`, the `post-merge` hook runs `sponsors:readme`, so the section is this branch's again.

(agent) Without `SPONSORS_SYNC_GITHUB_TOKEN`, a terminal run asks for the token (masked); without a terminal (CI, piped input) it fails saying which token it needs. Every way of not getting a token is a `SponsorsSyncError`, matched exhaustively, so a new error type is a type error.
- Human, 2026-10-19: "i want to automate the sponsors sync for vNext, maybe as a daily job [...] i don't want it to commit just for order/weight changes, only if a new sponsor is added/deleted"; "also the env name for this should be self-document". Human, on the trigger while `main` is the default branch: "Stay off `main`: keep the dormant daily cron, and also run on every push to `v12` until the cutover", then "on every push is probably aggressive as we'll be pushing a lot, make sure it's debounced"; on landing: "Commit and push straight to `v12` as github-actions[bot]".
- (agent) `.github/workflows/next-sponsors.yml` runs `sponsors-sync.ts --only-when-sponsors-change`, which writes nothing while `sponsors.json` lists the same logins in the same tiers, and pushes `sponsors.json` and the README to the branch only when they changed; new weights and ranks ride along with the next join, leave or tier change (a tier change counts because it moves a sponsor in or out of the partners). Its daily cron only fires from the default branch, so until `v12` is `main` pushes to `v12` stand in, at most one sync per UTC day (an `actions/cache` entry keyed by the date, saved after every attempt, failed ones too, so an expired token fails once a day rather than on every push) and one at a time (`concurrency`). `workflow_dispatch` and the cron skip the daily check. The bot pushes with `GITHUB_TOKEN`, which starts no workflow, so its commit neither loops nor runs `next.yml`.
- Human, 2026-10-19: "make sure the ci job also handles that some other person may be pushing at a similar time so it doesn't just fail / it can likely retry the rewriting of the commit or somethign since we require a linear history on the branch".
- (agent) When the push is rejected because the branch moved on, the job doesn't rebase (a shallow checkout, and a conflict in the README's sponsors section, would fail it): it waits a few seconds (longer each time, with jitter), resets to the branch's new tip, puts back the `sponsors.json` it synced, redoes the README's section from it (`--readme-only`), and commits and pushes again, up to six times. The commit always sits on the tip, so the history stays linear; if the tip already has those sponsors, it stops without a commit.
- (agent) The token is the `SPONSORS_SYNC_GITHUB_TOKEN` secret and env var, named for its one use (the repo's `TRPC_GITHUB_TOKEN` secret is another token, `dependabot-approve.yml`'s): a classic token of KATT's with `read:user` and `read:org`, both read-only. A fine-grained token can't do it: GitHub's GraphQL API doesn't take them, and they have no Sponsors permission. Without the secret the workflow warns and skips.
- (agent) On the first real run, 2026-10-19, GitHub sent `null` for every `lifetimeReceivedSponsorshipValues` node of both accounts, to `gh`'s token and to the classic one alike, with no error, while tiers and the activity log came through. So what a sponsor paid is now summed from the accounts' `sponsorsActivities` (all time, private ones included): every month a monthly tier was held, at its price then, from when it was picked to the next tier change, cancellation or now; a one-time tier once; minus refunds. It's an estimate (a cancellation's date and GitHub's proration move it by a month), close enough to weigh bubbles; the few log entries GitHub sends as `null` are skipped.
