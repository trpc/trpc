# No `throw` in Effect code; `throw` stays for misuse and Promise edges (human asked)

- Human, 2026-10-18: "Should we even `throw` in the vNext codebase now that we're effect native? Should we ban it with some specific exceptions? Wdyt?", then, on the rules below: "Do it."
- (agent) Not a blanket ban. Effect itself throws (its `src` has 500+ `throw`s: `*Sync` APIs, `RangeError`/`TypeError` on misuse); its line is that expected failures are typed and bugs may throw. The rules:
  - **Never in Effect code.** No `throw` in an `Effect.gen`/`Effect.fn` body or a callback handed straight to an `Effect.*` or `Stream.*` combinator: Effect makes it a defect, so a failure meant to be typed reaches the client as a masked `INTERNAL_SERVER_ERROR`. Fail with `yield* err`/`Effect.fail(err)`, or `Effect.die(err)` for a bug. `Effect.try`/`tryPromise` are the bridge from code that throws. The `trpc/no-throw-in-effect` lint rule enforces this on code built on Effect (`packages/*/src`, `tooling`, `test`, `examples/effect`), with no exceptions; it had one hit (a test's fake Redis), fixed with `Effect.die`.
  - **Internals don't throw `TrpcError`s.** tRPC's own failures are `failure(Reason.X(…))` values in an Effect's error channel ([`error-reasons.md`](./error-reasons.md)). 15 sites still throw one, all in code not yet on Effect ([`internals-use-effect.md`](./internals-use-effect.md)): `openapi/handler.ts` and `openapi/routes.ts` (behind `Effect.promise`), `server/socket.ts`, `openapi/link.ts`, `httpLink`'s `fetch` wrapper and `serializeInput`.
  - **Allowed:** public edges that promise throwing (Promise rejections, `result: 'throw'` actions, iterators handed to users, the Next control-flow rethrow); shapes a host fixes (framework hooks' "wrap in `<TrpcProvider>`", error boundaries rethrowing, TanStack's `throwOnError`, oxlint visitors); misuse caught at definition time in synchronous constructors (`mergeRouters` duplicate keys, `switchLink` names, `tracked('')`), as `TypeError`/`RangeError` or `Error`, never `TrpcError`, since it's a bug in the caller's code; tests and examples, whose resolvers throw like users' do.
  - **Serializers keep throwing.** They're synchronous and replaceable, so callers guard them anyway, like Effect's `Schema.decodeUnknownSync`; the handler converts with one `Effect.try`. `server/fetch.ts` no longer throws, catches, rethrows and casts around `deserialize`.
- Why: a `throw` inside Effect code silently turns a typed failure into a defect, which is the bug this rewrite's error model exists to prevent; banning it everywhere would fight hosts and public Promise APIs for no gain.
- Lost: one rule with no judgement calls. The allowed list is a convention, not enforced.
- Open: a second rule, `no-thrown-trpc-error` on `packages/*/src` outside tests, with overrides for the public edges, once the OpenAPI handler and the socket server move to Effect and the sites above are gone.
- Lives in: `tooling/oxlint-plugin/no-throw-in-effect.ts` and its test, `vite.config.ts` (the Effect-code override), `test/integration/publisher-recipes.test.ts`, `packages/trpc/src/server/fetch.ts`.
