# No `throw` in Effect code; `throw` stays for misuse and Promise edges (human asked)

- Human, 2026-10-18: "Should we even `throw` in the vNext codebase now that we're effect native? Should we ban it with some specific exceptions? Wdyt?", then, on the rules below: "Do it."
- (agent) Not a blanket ban. Effect itself throws (its `src` has 500+ `throw`s: `*Sync` APIs, `RangeError`/`TypeError` on misuse); its line is that expected failures are typed and bugs may throw. The rules:
  - **Never in Effect code.** No `throw` in an `Effect.gen`/`Effect.fn` body or a callback handed straight to an `Effect.*` or `Stream.*` combinator: Effect makes it a defect, so a failure meant to be typed reaches the client as a masked `INTERNAL_SERVER_ERROR`. Fail with `yield* err`/`Effect.fail(err)`, or `Effect.die(err)` for a bug. `Effect.try`/`tryPromise` are the bridge from code that throws; their options are object literals, so the rule never sees their callbacks as direct arguments. The `trpc/no-throw-in-effect` lint rule enforces this on code built on Effect (the override in `vite.config.ts`: `packages/*/src`, `tooling`, `test` and the Effect examples), with no exceptions. Its hits were tests: a fake Redis and two "not a stream" checks, now `Effect.die`.
  - **Internals don't throw `TrpcError`s.** tRPC's own failures are `TrpcError.<Code>` values in an Effect's error channel ([`granular-errors.md`](./granular-errors.md)). Six sites still throw one, each in synchronous code a caller converts: the OpenAPI handler's body check (`openapi/handler.ts`) and path-param decoding (`openapi/rest/routes.ts`), `experimental_openApiLink`'s contract lookup (`openapi/link.ts`), `httpLink`'s `fetch` wrapper on a serializer mismatch (`client/links/http/transport.ts`), and the serializer guards `deserializeInput` (`server/handler/fetch.ts`) and `serializeInput` (`client/links/events.ts`).
  - **Allowed:** public edges that promise throwing (Promise rejections, `result: 'throw'` actions, iterators handed to users, the Next control-flow rethrow); shapes a host fixes (framework hooks' "wrap in `<TrpcProvider>`", error boundaries rethrowing, TanStack's `throwOnError`, oxlint visitors); misuse caught at definition time in synchronous constructors (`mergeRouters` duplicate keys, `switchLink` names, `tracked('')`), as `TypeError`/`RangeError` or `Error`, never `TrpcError`, since it's a bug in the caller's code; tests and examples, whose resolvers throw like users' do.
  - **Serializers keep throwing.** They're synchronous and replaceable, so callers guard them anyway, like Effect's `Schema.decodeUnknownSync`.
- Why: a `throw` inside Effect code silently turns a typed failure into a defect, which is the bug this rewrite's error model exists to prevent; banning it everywhere would fight hosts and public Promise APIs for no gain.
- Lost: one rule with no judgement calls. The allowed list is a convention, not enforced.
- Open: a second rule, `no-thrown-trpc-error` on `packages/*/src` outside tests, with overrides for the public edges, once the six sites above fail in an error channel instead.
- Lives in: `tooling/oxlint-plugin/no-throw-in-effect.ts` and its test, `vite.config.ts` (the Effect-code override), `test/integration/publisher-recipes.test.ts`.
