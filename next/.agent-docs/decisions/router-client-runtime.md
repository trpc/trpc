# In-process clients take a caller-owned `ManagedRuntime`, not a layer (human)

- Question: "`createRouterClient(router, { layer })` and `localLink({ layer })` build a `ManagedRuntime` on the first call and never dispose it, so layer finalizers never run and each client leaks its pool in tests. Recommended: take a caller-owned `ManagedRuntime` instead of a layer (Effect-native, no new client method; the handler could take the same)."
- Human, 2026-10-19 (first-release review, question 2): "sure".
- (agent) `createRouterClient(router, { ctx, runtime })` and `localLink({ router, runtime })` take `runtime: ManagedRuntime.ManagedRuntime<inferRouterServices<TRouter>, unknown>`, required exactly when the router needs services (`RuntimeOption`, beside `LayerOption`). They never build or dispose a runtime: the caller makes it with `ManagedRuntime.make(layer)` and disposes it (`await using`, `runtime.dispose()`), which runs the layer's finalizers. Clients sharing a runtime share one build. `createTrpcRsc` takes it through `RouterClientOptions`.
- (agent) `layer` is gone from both, with no alias since nothing has shipped. It stays as `layer?: TypeError<'pass \`runtime: ManagedRuntime.make(layer)\` instead of \`layer\`, and dispose the runtime when done'>`, so passing one is an error that names the fix; leaving the key out would give "Object literal may only specify known properties", and an options object built elsewhere (a test helper's `{ ctx, layer }`) would only report the missing `runtime`.
- (agent) The services are read per call through `runtimeServices` (`server/execution`), shared with the handler core: `runtime.cachedContext` when built, else `Effect.orDie(runtime.contextEffect)`. Reading `contextEffect` per call matters: a disposed runtime swaps it for `Effect.die('ManagedRuntime disposed')`, while one captured at link creation would keep handing out the released context. A call after `dispose()` and a call whose layer fails to build are both an unexpected `INTERNAL_SERVER_ERROR` whose `cause` is the defect or the layer's error, as over HTTP; the layer's error type isn't in the client's error union, so it can't be a typed failure.
- (agent) `call(procedure, input, { layer })` keeps `layer`, built for the call and released when it returns.
- Why: Effect owns resource lifetimes through `ManagedRuntime`/`Scope`; a client has no end of life of its own to release a layer at, so whoever starts the resources should stop them. One runtime can then back a router client, a `localLink` and Effect code elsewhere in the app, built once. No new client method (`client.dispose()`) or `Symbol.asyncDispose` on the proxy, whose keys are procedure paths.
- Lost: the one-liner `createRouterClient(router, { layer })`; callers now write `ManagedRuntime.make(layer)` and own its disposal. A forgotten `dispose()` still leaks, but in the caller's code, where `await using` fixes it.
- Open: should `createFetchHandler` (and the WebSocket, OpenAPI and interop handlers) also take `runtime` as an alternative to `layer`? It would let a server share one pool between the handler and an SSR router client; `handler.dispose()` would then leave a caller-owned runtime alone. Recommended: yes, as a follow-up, keeping `layer` there since the handler does release it.
- Open: `experimental_createAction({ layer })` (`src/actions/index.ts`) builds a `ManagedRuntime` per factory and never disposes it, the same leak; it's experimental, so it can follow this shape when it stabilizes.
- Open: `call()` on a subscription resolves to an Effect `Stream` while its type says the event type; the router client returns an `AsyncIterable`.
- Lives in: `packages/trpc/src/server/caller.ts`, `src/client/links/local.ts`, `src/server/handler/fetch.ts` (`RuntimeOption`), `src/server/execution/execute.ts` (`runtimeServices`), `src/effect/effect.test.ts`, `src/server/procedures/procedures.test.ts`, `docs/server/server-side-calls.md`, `docs/client/links/local.md`, `docs/server/effect.md`.
