# The OpenAPI handler refuses cross-origin form bodies by default (human)

- Human, 2026-10-19 (decision round, a CSRF guard on the OpenAPI handler before the first publish): "on by default".
- `experimental_createOpenApiHandler` answers `403 FORBIDDEN` (`Cross-origin POST requests must send content-type: application/json`) to a request from another origin that uses a method other than `GET`, `HEAD` or `OPTIONS` with a body that isn't `application/json`. The check runs before `createContext`, before the body is read, and in `serve()` too, so `@trpc12/experimental-nest` gets it. `csrf: false` turns it off.
- (agent) Detection follows Go 1.25's `http.CrossOriginProtection`. `Sec-Fetch-Site` decides when present: `same-origin` and `none` (the user's own navigation) pass, while `same-site`, `cross-site` and anything else are refused. Without it, an `Origin` header has to name the request URL's host (`Origin: null` never does). With neither header, the request isn't from a browser and passes.
- (agent) Sibling subdomains count as other origins, as in Go, SvelteKit and Astro. `same-site` would let a compromised or user-content subdomain post forms. `csrf: { trustedOrigins: ['https://www.example.com'] }` lets listed origins through, matched exactly against `Origin`. Entries that aren't bare origins throw at creation.
- (agent) What counts as "form-style" is an allowlist: only `application/json` skips the check. That covers the three CORS-safelisted types (urlencoded, multipart, `text/plain`), a missing `content-type` (a `no-cors` `fetch` of a `Blob`, or an empty body that would run a no-input mutation) and anything added later. The server splits the media type the same way browsers do, so a header that a browser counts as safelisted is never read as JSON here.
- Why: HTML forms and `no-cors` fetches reach the handler from any site, with the user's cookies and no CORS preflight. The OpenAPI handler accepts urlencoded and multipart bodies by design, so it can't use the RPC handler's rule (JSON-only bodies plus `trpc-version` on multipart, [`plugins-are-effect-middleware.md`](./plugins-are-effect-middleware.md)). `SameSite` doesn't fill the gap: only Chrome defaults cookies to `Lax`, and same-site attackers bypass it. Fetch Metadata needs no token or client change. Scoping the check to non-JSON bodies leaves preflighted cross-origin JSON to `cors()`, so a browser app on another origin keeps working with the API.
- Prior art: Go's `CrossOriginProtection` (Fetch Metadata, then `Origin` against `Host`, plus trusted origins), SvelteKit's `csrf.checkOrigin` and Astro's `security.checkOrigin` (both on by default; `Origin` must equal the URL's origin for form content types), Hono's `csrf()` (`Origin` or `Sec-Fetch-Site` for form content types), and Next.js Server Actions (`Origin` against `Host`, with `allowedOrigins`). oRPC v2 has no guard for unsafe methods; its `GetMethodCsrfProtectionHandlerPlugin` covers `GET` navigations only ([`packages/server/src/plugins/get-method-csrf-protection.ts`](https://github.com/middleapi/orpc/blob/v2.0.0-beta.44/packages/server/src/plugins/get-method-csrf-protection.ts)).
- Lost:
  - Go's check of every unsafe request, whatever its body: it would refuse CORS-allowed cross-origin JSON clients unless each origin were listed.
  - Synchronizer tokens: they need state and a client that reads them.
  - Without `Sec-Fetch-Site`, comparing only the host lets an `http://` page on the same host through to an `https://` API, as in Go. HSTS covers that, and every browser has sent Fetch Metadata since 2023.
  - Behind a proxy that rewrites `Host`, old browsers' same-origin forms are refused unless their origin is trusted.
- Open: `GET` routes on mutations (`.route({ method: 'GET' })`) aren't checked; that is oRPC's navigation guard, if wanted.
- Lives in: `packages/trpc/src/openapi/rest/csrf.ts` (`makeCsrfGuard`, `CsrfOptions`), the `csrf` option in `packages/trpc/src/openapi/handler.ts`, tests in `packages/trpc/src/openapi/csrf.test.ts`, docs in `docs/openapi/routes.md#cross-site-forms`.
