# Streamed responses and WebSocket sends wait for the client (human)

- Human, 2026-10-18, on the open point about WebSockets (A was "make WebSocket sends wait for a slow client before 1.0"): "A)
  also fix this with a pr on `main` if its an issue"
- (agent) A streamed query, a deferred value, a batch, a subscription's SSE stream, an OpenAPI subscription and the v11 interop's JSONL batch only read the procedure as fast as the client reads the response. The internal `Stream.callback` queues are bounded (`backpressure` in `internal/effects.ts`, 16 items, `Queue.offer` suspends), and OpenAPI's SSE body is a pulled `ReadableStream`. A generator behind a paused client stops at its `yield`; when the client leaves, the generator's `return()` runs. Before this, the server read the whole stream into memory while the socket was full: a 1 KB-per-yield generator went from 5k yields (bounded) to all of them.
- (agent) WebSockets: a session's outbox (`runSocket`) is a bounded `Queue` too (`backpressure.bufferSize`, `Queue.offer` suspends), and its writer fiber, after each write, waits while the socket holds more than `sendHighWaterMark` (64 KiB) of unsent bytes, looking every 10 ms since WebSockets have no drain event. `Connection.send` and `SocketOutbox.send` return Effects, so `emitEvents`, deferred chunks and the v11 session's events pull the next item only once the frame is queued. A 1 KiB-per-yield generator behind a client that stops reading stops after 79 yields (63 in the socket, 16 in the outbox); before, the socket held 31 MB and growing.
- (agent) Effect's `Socket` writes without waiting and keeps its `WebSocket` to itself, so whoever holds the platform's socket says how to read its unsent bytes (`withBufferedAmount`): `handler.websocket(ws)` and `websocket.upgrade` read the standard `bufferedAmount` (Deno, `ws`), which `WebSocketLike` now has as an optional field; Node's `request.upgrade` reads the upgraded TCP socket's `writableLength`, which is what `ws` counts. Raw TCP sockets (`serveSocket()`) need nothing more: Effect's `NodeSocket` writer already waits for `drain`, and the bounded outbox passes that on.
- (agent) Replies to `ping`, `init` and bad messages go through the same outbox, so a client that sends but doesn't read stops being read, as TCP would. A close (idle timeout, protocol error) flushes what's queued without waiting and then closes. When the peer is gone, the outbox drops what's queued and lets waiting senders go, so stopping calls can't hang on a dead socket.
- (agent) `serveAsWebSocket` (another library's `websocket()` handler under `toHttpEffect()`): its `send` is synchronous by contract, so it queues in front of the outbox, and its `bufferedAmount` counts what's queued plus the socket's unsent bytes, for that handler to wait on.
- (agent) Not covered, because the platform gives no signal: Bun's `request.upgrade` (Effect's Bun server drops `sendText`'s backpressure result and keeps the `ServerWebSocket`), Workers' `WebSocket` (no `bufferedAmount`, so `websocket.upgrade` on Workers and Cloudflare hibernation send at once), and MessagePorts (`postMessage` queues on the other side, with nothing to read). Their writes don't wait, so the bounded outbox never fills.
- Why: an unbounded queue in front of a slow or stalled client is a memory leak per connection, and Effect's Node server already waits for `drain` on stream bodies, so the queue was the only thing in the way. Generators are lazy in JavaScript; reading them ahead only makes sense up to a small buffer. On a WebSocket every subscription on the connection shares the socket, so one slow client grew the server's buffers for all of them.
- Lost: a producer that is faster than its client now waits for it. One that has to finish on its own schedule should run in the background (for example a publisher) and stream from there. On a WebSocket, a full outbox makes every call on that connection wait, not just the subscription that filled it, and a stalled connection polls its socket every 10 ms.
- Open: Bun and Workers need an upstream signal: Effect's Bun `upgrade` could expose `getBufferedAmount()` or wait on `sendText`'s result; Workers would need `bufferedAmount`.
