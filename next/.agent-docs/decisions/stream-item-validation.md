# Stream items are validated with `stream()`; subscriptions accept either form (human)

- Human, 2026-10-15 (decisions round 3, Q13 = proposal 14 Q14.3): "A but B should work too specifically for subscriptions (allow that to have either or)".
- Subscriptions: `.output(Post)` and `.output(stream(Post))` both validate each event (the `data` of `tracked()` events).
- Streamed queries and mutations: `.output(stream(Item, Return?))` validates each yielded item and the generator's return value. The client sees `AsyncIterable<Item>` or `AsyncGenerator<Item, Return>`.
- (agent) A plain `.output(Item)` on a query or mutation whose resolver returns a generator or `Stream` is a type error pointing to `stream()`.
- (agent) A bad item fails the stream with `INTERNAL_SERVER_ERROR` after the items before it are delivered, like a bad output today. `{ validate: false }` types items without checking them.
- (agent) Streams nested inside an object output are not validated in v1; schema libraries can't hold a `stream()` field.
- (agent) Deserialized async iterables now end with the stream's return value, so `iterator.next()` gives `{ done: true, value: summary }`; the client type keeps the return type when it isn't `void` or `any`.
- (agent) A `stream()` output's OpenAPI document describes the item schema.
- (agent, 2026-10-19, [`effect-internal-patterns.md`](./effect-internal-patterns.md)) A streamed output is one `Channel` from the resolver's `Stream` or iterable (`Channel.fromAsyncIterableArray`, whose done value is the generator's return value) to the `AsyncIterable` callers get: failures are settled with `Channel.catchCause`, items validated with `Channel.mapEffect` and the return value with `Channel.mapDoneEffect`, and it leaves once, through `Stream.toAsyncIterableWith` (`streamedOutput` in `execute.ts`), whose iterator then ends with the return value as a generator does. Before, two `async function*` wrappers (`settleIterable`, `validateItems`) each ran an Effect per item through `Effect.runPromiseWith`, and a `Stream` output was turned into an iterable and back. Middleware still sees the iterable; output validation extends its channel instead of iterating it. Lost: a `next()` still pending when `return()` is called now resolves `done`, dropping the item in flight (Effect's iterator interrupts the pull), where the generator wrapper resolved it with the item; a `Stream` output already did this. `for await` never overlaps the two.
- (agent, 2026-10-20, decided under [`effect-first-public-apis.md`](./effect-first-public-apis.md)) That drop stays: a `return()` during a pending `next()` resolves it `done` and loses the item in flight, as Effect's `Stream.toAsyncIterable` does. Waiting for the pull instead would need a hand-rolled iterator around Effect's, for a case `for await` never produces.
- Why: the common subscription case stays short, the ambiguous cases are explicit, and return values get a schema.
- Lost: one rule for every kind.
- Lives in: `packages/trpc/src/server/validation/stream-schema.ts`, `src/server/execution/execute.ts` (`validateItems`, `streamedOutput`), `src/server/procedures/builder.ts` (`StreamOutputCheck`), `src/contract/index.ts`, `src/transformer/progressive-json/stream.ts` (return values); `packages/trpc/src/server/execution/stream-output.test.ts`.
