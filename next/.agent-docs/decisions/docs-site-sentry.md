# The docs site reports its errors and a sample of its traces to Sentry (human asked)

- Human, 2026-10-20 (via the coordinator): "I'll also want to add sentry and wire you up to it".
- (agent) `@sentry/tanstackstart-react` (11.8.0), in the browser and in the `_ssr` function ([`docs-flags-on-demand.md`](./docs-flags-on-demand.md)). The build reads its settings from its environment: the DSN (`SENTRY_DSN`, or `NEXT_PUBLIC_SENTRY_DSN`, which Sentry's Vercel integration sets), the environment (`VERCEL_ENV`), the release (the commit), a `branch` tag, and `SENTRY_TRACES_SAMPLE_RATE` (5% by default). Without a DSN the site reports nothing and loads nothing more; without `SENTRY_AUTH_TOKEN`, `SENTRY_ORG` and `SENTRY_PROJECT` the build uploads no source maps and is what it was. Local, CI and preview builds without them pass as before.
- (agent) In the browser, the entry only has a shim (+0.5 KB gzip on a page's JS) that queues errors: the window's `error` and `unhandledrejection`, and `hydrateRoot`'s hooks, so what React catches, can't recover from, or recovers from (a hydration mismatch) is reported, and the router's not-found and redirects aren't. The SDK's chunk (51 KB gzip) loads once the page is idle after `load` when traces are sampled, otherwise at the first error, and traces page loads and navigations by route (`/v12/docs/$`). No session replay and no session per page view; an event has no IP address, cookies, headers or bodies (URLs keep their query: the flags a page rendered), and only the site's own scripts' errors count (`allowUrls`).
- (agent) The release comes to the browser in the page, through the router's `dehydrate` and `hydrate`, not in a chunk: there, the commit renamed about 25 chunks (424 KB gzip, the entry included) on every deploy, even one that changed nothing else.
- (agent) On the server, Sentry starts in the `_ssr` function and not in the prerender (`TSS_PRERENDERING`), where an error fails the build. It reports what the request handler throws and, since React's render errors only reach `console.error`, what's logged there, and traces requests.
- (agent) With the upload credentials, the build gives every chunk a debug ID, writes hidden source maps (no `sourceMappingURL`), uploads them and deletes them from `dist`, so none are deployed. A failed upload warns and the build goes on. Measured locally on a warm cache: about 20 s and 0.8 GB more at peak (5.2 GB), and +5.6 KB gzip on a page's JS, the debug IDs' share; the server bundle is 1 MB bigger, DSN or not.
- Why: errors on the live site (hydration mismatches above all, which only show in a visitor's browser) reach someone, with readable stacks, at the cost of half a kilobyte before an error happens; and agents can read them through Sentry's MCP server, set up outside the repo.
- Lost: errors before the entry runs (the inline theme script); events from browsers whose ad blocker blocks Sentry (the site is static, so there's no tunnel); traces from visitors who leave before the page is idle; without uploads, the 5.6 KB; release-based source maps would save them, the way Sentry no longer recommends.
- (agent, 2026-10-20) Every not-found URL under `/docs`, `/v12` and the root hydrated `404.html`, rendered for `/404`, as its own path's not-found, and mismatched (React #418, live before Sentry), which would have been Sentry's most frequent issue. Now the router reads such a URL as `/404` ([`docs-website-on-vercel.md`](./docs-website-on-vercel.md)).
- Open: the sample rate, once there's traffic to look at.
