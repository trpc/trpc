# Every distinct failure has its own `_tag`; its `code` stays for `switch`, `matchError()` and the wire (human asked)

- (superseded) Human, 2026-10-15 (decisions round 3, Q5): "A". Every `TrpcError` had `_tag` equal to its `code`, so `Effect.catchTag('NOT_FOUND', …)` took a code out of the union, the declared `NOT_FOUND` and the built-in one together.
- Human, 2026-10-20 (on `trpc-error-reason`, whether tRPC's own errors carry a tagged `reason` inside their code): "Do a) but also the short list in c of things that clients can act on". Option A kept codes, classes and messages; C put a short list of serialized reasons on the wire. Superseded the same day, before it was built, by the next answer, which turns that list into tags.
- Human, 2026-10-20 (on `effect-catch-tag-built-in-errors`, whether `Effect.catchTag('NOT_FOUND')` keeps catching the built-in `NOT_FOUND`): "I think every distinct error should have a tag if that's the effect way, rather than following http verbs. For non effect users we can map them to codes and have same DX as today". Earlier context: "Isn't the effect way that every internal error has its own tag?"
- (agent) `_tag` names the failure, `code` names its HTTP-ish class. A built-in code's class is tagged with its name: `NOT_FOUND` is `TrpcError.NotFound`, tagged `NotFound`, and so are `error({ code: 'NOT_FOUND' })` and `TrpcError.Tagged('NOT_FOUND')`. A custom code's tag is the code (`error({ code: 'OUT_OF_STOCK' })` is tagged `OUT_OF_STOCK`). A `TrpcError.Tagged` class's tag is its first argument, and it takes `code` to name another: `Tagged('PostMissing', { code: 'NOT_FOUND' })` is a 404 that `switch (err.code)` treats as `NOT_FOUND` and `Effect.catchTag('PostMissing')` catches alone. `.errors({ NOT_FOUND: PostMissing })` keeps the class's tag in the type.
- (agent) tRPC's own failures get specific tags on their code's class (`new TrpcError.PayloadTooLarge({ tag: 'BatchTooLarge' })`, typed: a tag of another code is a type error). The list, in `FailureTags` in `internal/error.ts`, with each one's code:
  - Sent to clients with their tag (`ClientTags`), since a client acts on them: `ProcedureNotFound` (`NOT_FOUND`: reload, the client is newer than the server), `ProcedureTypeMismatch` (`METHOD_NOT_SUPPORTED`: reload, client and server disagree on query vs mutation), `SerializerMismatch` (`UNSUPPORTED_PROTOCOL`: the link and the handler use different serializers; the link makes it).
  - Server-only, seen by `onError`, `Effect.catchTag` in middleware and internal channels: `RouteNotFound`, `InvalidInput` (`BAD_REQUEST`, defined, so it reaches clients too), `InvalidOutput`, `InvalidBody`, `MissingInputField`, `UnreadableBody`, `BodyConsumed`, `ByteStreamConsumed`, `BatchTooLarge`, `BatchingDisabled`, `InvalidBatch`, `InvalidPathParam`, `CrossSiteRequest`, `InvalidMessage`, `UnknownMessage`, `InvalidRequestId`, `ProcedureNotImplemented`, `UnsupportedResponse`, `CallIdConflict`, `InvalidDurableHeader`, `InvalidConnectionToken`, `ConnectionTokenExpired`.
  - A failure that is just its code's meaning keeps its code's class: a body over `maxBodySize` is `PayloadTooLarge`, a timed-out `signal` is `Timeout` ([client-timeout-error](./client-timeout-error.md)), no response is `NetworkError`, a cut stream is `StreamInterrupted`.
- (agent) The wire carries `tag` only when it isn't the code's default and the client keeps it: a defined error's own tag (`InvalidInput`, `PostMissing`) and the three client tags. The RPC error body, socket frames and OpenAPI bodies (`OpenApiErrorBody.tag`, and `tag: { const }` in the generated error schemas) share the rule (`wireTag`). `fromWireError` reads it; `toUntypedError` folds any other built-in tag to its code's class, keeping the original as `cause`, so a `localLink` client sees what an HTTP one does. v11 clients and OpenAPI callers that don't read `tag` see the same code and status as before.
- (agent) Promise clients don't change: `err.code`, `switch (err.code)` and `matchError()` keyed by code. `BuiltinError` gains one member per client tag, so `err._tag === 'ProcedureNotFound'` narrows inside `case 'NOT_FOUND'`.
- (agent) Effect: a call's error channel is a union of tagged errors, and `Effect.catchTag('NotFound')` takes exactly that failure, leaving `ProcedureNotFound`. No `catchCode` helper: `hasCode(code)` is a refinement, so Effect's own `Effect.catchIf(hasCode('NOT_FOUND'), …)` takes every error with a code, and it costs nothing in the client bundle when unused.
- (agent) Cost, on TS 7.1 (`pnpm bench shapes`, 1,500 procedures, against `f6d422bad`): server half, `errors` +3.6% instantiations (988,718 to 1,024,788), `plain` and `match` +0.01%; with the client, `plain` +0.6%, `match` +1.8%, `errors` +3.1%, `effect client` +4.1% (1,834,358 to 1,910,407). Check times moved within noise. Client bundle, gzip -9: minimal JSON client +156 B (39,814 to 39,970), full client +177 B (44,115 to 44,292), for the client tags and the wire field. Formulation: one indexed lookup per built-in code (`CodeTags[TCode]`), the custom code itself as its tag (no template-literal case conversion), and a tag type parameter on `TrpcError` defaulting to `TagOfCode<TCode>`; class tags are made from the codes at load, not shipped as strings.
- Why: Effect narrows by `_tag`, one per failure ("the effect way"), and a code lumped a missing procedure with a missing record. Tags on the codes' classes keep the HTTP grouping for Promise users, and sending tags only where a client acts keeps the payload and the client's types small.
- Lost:
  - `_tag` equal to the code: `Effect.catchTag('NOT_FOUND')` no longer exists; it's `catchTag('NotFound')`, or `catchIf(hasCode('NOT_FOUND'))` for every `NOT_FOUND`.
  - A `reason` field inside the code: [#7677](https://github.com/trpc/trpc/pull/7677)'s never-serialized `Data.TaggedEnum` of about 60 reasons with a table fixing each one's code and message (`trpc-error-reason` B), and the serialized short list (C), are both tags now. Reasons' fields (`BodyTooLarge { limit }`, `ProcedureNotFound { path }`) are messages.
  - A `catchDefined` helper and a single `TrpcError` tag for built-in errors (`effect-catch-tag-built-in-errors` B and C): with a tag per failure, `catchTag` already catches only the declared error.
- Open: tags for client-side failures beyond `SerializerMismatch` (a link's own decode failures are `BadResponse`), if a client needs to act on one. A `ProcedureNotFound` still doesn't say the client is stale for certain ([stale-client-error](./stale-client-error.md)).
- Lives in: `packages/trpc/src/internal/error.ts` (`CodeTags`, `FailureTags`, `ClientTags`, `TagOfCode`, `Failure`, `wireTag`, `hasCode`, `TrpcError.Tagged`), `src/client/types.ts` (`BuiltinError`), `src/server/procedures/builder.ts` (`DeclaredErrors`), `src/openapi/rest/errors.ts` and `src/openapi/generate.ts`, and each failure site; tested in `src/server/errors.test.ts`, `src/server/tagged-errors.test.ts`, `src/effect/effect.test.ts`, `src/serializer/protocol.test.ts`, `src/openapi/openapi.test.ts`; documented in `www/docs/server/errors.md#in-effect-code`, `www/docs/client/errors.md#the-failures-a-client-acts-on` and `www/docs/client/effect.md#errors`.
