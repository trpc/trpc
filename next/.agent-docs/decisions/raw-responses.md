# Procedures may return an `HttpServerResponse` on unbatched HTTP calls (human)

- Human, 2026-10-15 (decisions round 3, Q11 = proposal 04 Q4.3): "Do c". Neither tRPC v11 nor oRPC lets a procedure return a response.
- A resolver may return Effect's `HttpServerResponse` (the core's response type, [`http-core-on-effect-http.md`](./http-core-on-effect-http.md)); a web `Response` is accepted and converted with `HttpServerResponse.fromWeb`. It is sent as is: status, headers, body (redirects, proxied upstreams, streams).
- (agent) Unbatched HTTP calls and in-process calls carry it. In a batch, over WebSockets or MessagePorts, the call fails with `BAD_REQUEST`. Clients get a web `Response` as the output (the type is `Response`), so a batching `httpLink` must send such procedures alone. The response carries `trpc-response: 1` so the link returns it instead of decoding it.
- (agent) OpenAPI routes send it as the route's response; the document describes it as an untyped response.
- Why: proxies, redirects and pre-built responses without leaving tRPC for a separate route.
- Lost: one transport-independent output type for every procedure.
- (agent) The client learns it from types, through a call option: `batch: false` (read by `httpLink`) sends a call alone, and `httpLink({ batch: true })` declares `{ batches: true }`, so on that chain a call to a procedure whose output may be a response (`Extract<Output, Response | HttpServerResponse>`) must pass `{ batch: false }`, a type error otherwise. No runtime contract, as `client.md` asks. `httpLink` uses overloads, not a generic, so it infers inside `switchLink`/`splitLink` options. Lost: automatic routing; a `batch: boolean` variable picks the non-batching overload.

## In-process calls (agent)

- The question (first-release review, 2026-10-19, question 10): "A procedure returning a `Response` is typed `Response` in-process but always fails with `BAD_REQUEST`. Recommended: in-process calls (`createRouterClient`, `localLink`, `call()`) return the web `Response`."
- Human, 2026-10-19 (first-release review, question 10): "what? i don't get this - make a call and defer".
- Deferred: the human asked the agent to decide; revisit before 1.0.
- (agent) In plain words: a procedure can answer with a whole HTTP response of its own (a redirect, a CSV download) instead of data. You can also call procedures directly in your own server code, without going over the network. Those direct calls used to fail every time with "bad request", although the types promised a response. Now a direct call gets the same response an HTTP client would get: its status, its headers and its body, which you can read as a stream.
- (agent) `createRouterClient`, `localLink` (with or without a serializer) and `t.call()` pass `allowResponse` and a response handle to `callProcedure`, then turn the `HttpServerResponse` into a web `Response` with `HttpServerResponse.toWeb` (`inProcessOutput` in `execute.ts`). The handle's headers go under the response's own, `set-cookie` appended, as `fetch.ts` does for HTTP; the handle's status is ignored, as over HTTP. A `localLink` serializer never sees the response. `t.call()`'s return type maps an `HttpServerResponse` output to `Response` (`CallOutput`), as the clients' `Deserialized`/`Framed` already did, so `t.call(proc)` is `Promise<Response>` for either kind. Declared and returned errors stay typed and arrive as before. Server actions (`actions/`) still refuse it: an action's result has to cross React's serialization, which a `Response` can't.
- (agent) In-process chains don't batch (`localLink` declares no `batches`), so no `{ batch: false }` is needed there.
- (agent) Why: the types already said `Response` for in-process clients, and only a `Response` the caller can read makes the procedure testable in process (status, `location`, body) without a server.
- (agent) Lost: in-process calls had the same "only over HTTP" rule as other transports; now they differ from WebSockets. The body is read through Effect's stream (`fromWeb` then `toWeb`) rather than handed over as the resolver's own object.
- (agent) Open: whether WebSocket and MessagePort calls should carry a response too (a status, headers and a byte body over the socket protocol); whether `t.call()` should return the resolver's own object by reference instead.
- Lives in: `packages/trpc/src/server/execution/execute.ts` (`isResponseValue`, `allowResponse`, `inProcessOutput`), `src/server/handler/fetch.ts`, `src/server/caller.ts` (`call`, `CallOutput`), `src/client/links/local.ts`, `src/client/links/http/` (overloads, `batch: false`), `src/client/types.ts` (`ProcedureCallArgs`), `src/internal/types.ts` (`ProcedureResponse`); tests in `packages/trpc/src/http/core.test.ts`; docs in `www/docs/server/responses.md`, `www/docs/server/server-side-calls.md` and `www/docs/client/links/local.md`.
