# One `TrpcError`, inferred and declared errors, no formatter (human)

- Human, 2026-10-15 (Q7.7): "A". One isomorphic `TrpcError` class, the same on server and client, with `code`, `status`, `data` and `defined`. No `TrpcClientError`.
- Human, 2026-10-15 (Q7.6): "A". No global `errorFormatter`. Logging goes to the handler's `onError`; shape changes are mapping middleware, whose returned errors the client infers.
- Why: the same checks work in resolvers, tests and the client, and every error shape is typed.
- Lost: v11's `TRPCClientError` wrapper and its untyped `errorFormatter`.
- (agent, Q7.1) Proposal 07's combined model. `TrpcError` is built on Effect's `Data.Error`, so it is yieldable. `error({ code, data?, message? })` constructs one; returned or failed errors are inferred into the procedure's error union.
- (agent) Declared errors (07 A): `.errors({ NOT_FOUND: { status?, message?, data?: schema } })` gives the resolver a typed constructor per code. A thrown error with a declared code is `defined`, from its constructor or not, even when thrown from helper code. `data` is validated, and invalid data is an unexpected error because sending it would break the client's types.
- (agent, Q7.3) `safe()` returns `[data, error]` that also has `{ data, error }` properties, so both destructuring styles work.
- (agent, Q16.4; human: "Revisit later. Pick something for now") Client-side failures are new codes in the same union (`NETWORK_ERROR`, `CLIENT_CLOSED_REQUEST`), not a flag.
- Masking is [`mask-unexpected-errors.md`](./mask-unexpected-errors.md).
- (agent) The Open here (tag errors by code for `Effect.catchTag`) is done: [`error-tags.md`](./error-tags.md).
- Human, 2026-10-16 (decision round, error status after oRPC v2): "C". `status` lives only on declared specs (`.errors({ X: { status } })`) and `TrpcError.Tagged` specs, as a hint the HTTP and OpenAPI handlers read. It is gone from `TrpcError` instances, `error()` and `new TrpcError()` options, REST error bodies and socket error frames. This narrows Q7.7's field list to `code`, `data` and `defined`.
  - Options were: A) keep `status` everywhere; B) oRPC v2's way, no `status` anywhere and a code-to-status map on the handlers; C) this. oRPC v2 removed it from `ORPCError` and its error bodies (`.repos/orpc/apps/content/docs/migrations/from-v1.mdx`, "`status` removed from errors").
  - Why: sockets and message ports have no status, and the brief says the protocol must not assume HTTP.
- (agent) A handler picks a status with `statusOf(err, declared?)`: the procedure's declared spec for the code, then a status hint, then the `TrpcError.Tagged` class's spec, then the built-in code's status, then `400`. A hint is kept in a WeakMap when an error is rebuilt (checking declared data, replaying a durable call), so a tagged class's status survives the rebuild.
- (agent) A `TrpcError.Tagged` instance's type has `'~status'?: TStatus`, type-only, so `experimental_generateOpenApiFromTypes` still documents an inferred tagged error's status.
- (agent) Clients map a non-tRPC HTTP response's status to a built-in code (`codeOfStatus`). `retryLink` and `durableLink` retry by code: a code whose built-in status is 5xx, or a network failure.
- (agent) A batch line keeps its own `{ i, status, body }`: that is the HTTP status of one call in a `207`, not a field of the error.
- Lost: a client can't read an error's HTTP status (`err.status`); it reads `code`. A custom code declared with a 5xx status isn't retried, since the client doesn't see the status. Socket and message-port calls never had a status; now the handlers alone decide it.
- Lives in: `packages/trpc/src/internal/error.ts` (`statusOf`, `withStatusHint`, `codeOfStatus`, `serverFailure`), `src/server/execution/declared.ts`, `src/server/handler/fetch.ts`, `src/openapi/handler.ts`, `packages/trpc/src/server/errors.test.ts`, `packages/trpc/src/server/tagged-errors.test.ts`.
