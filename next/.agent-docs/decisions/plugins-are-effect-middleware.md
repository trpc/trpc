# No plugin interface: Effect HTTP middleware and root middleware instead (human)

- Human, 2026-10-15 (decisions round 3, Q10 = proposal 13 Q13.1 to Q13.3): "C".
- Request-level concerns (CORS, rate limits, logging, auth headers) are Effect `HttpMiddleware` around the handler's `effect/http` app: `createFetchHandler({ router, middleware: [HttpMiddleware.cors({ … })] })`. `serve()`'s `allowOrigin` becomes Effect's CORS middleware.
- Call-level concerns are root `t.use()` middleware.
- Protocol rules stay fixed handler options: `maxBodySize`, batching opt-in, mutations over `POST`, JSON-only `POST` bodies, and the `trpc-version` header on multipart ones (CSRF). They can't be turned off by a plugin.
- Why: Effect already ships CORS, logging and tracing middleware; a second middleware system would duplicate both layers. Follows [`http-core-on-effect-http.md`](./http-core-on-effect-http.md).
- Lost: an oRPC-style `{ onRequest, onCall }` plugin interface and switch-off-able protocol features.
- (agent) `@trpc12/trpc/http` exports `cors(options)`, Effect's `HttpMiddleware.cors` that also answers `403` to WebSocket upgrades from origins it doesn't allow (browsers don't preflight upgrades). `serve({ allowOrigin })` is gone; pass `middleware: [cors({ allowedOrigins })]`.
- (agent) Q13.2 follows from "C": there are no plugins to switch on. What 13 proposed on by default is built in and always on: the body limit (`maxBodySize`), strict methods (queries `GET`/`QUERY`, mutations `POST`) and the CSRF rule (JSON-only `POST` bodies). The proposed opt-ins are Effect middleware or links: `cors()`, `rateLimit()`, `durable()`, `retryLink`, `dedupeLink`.
- (agent) Found 2026-10-16, security: the CSRF rule had a hole. `readInput` in `src/server/handler/fetch.ts` takes `multipart/form-data` for any `POST`, and the JSON-only check applies only to the other bodies. A cross-site `<form enctype="multipart/form-data">` with an `input` field of `{"json":{…}}` therefore runs any mutation; a probe against `createTestServer` got a 200 and the resolver ran. Browsers' default `SameSite=Lax` cookies limit this to same-site origins and `SameSite=None` cookies, but the rule promises more. oRPC v2 replaced its CSRF plugin pair with a `Sec-Fetch-*` check that needs no client cooperation (`GetMethodCsrfProtectionHandlerPlugin`), and its RPC handler rejects `GET` unless `allowMethods` lists it. Options: A) require the `trpc-version` header on multipart requests (`httpLink` already sends it on every request, and a custom header forces a CORS preflight); B) reject `Sec-Fetch-Site: cross-site` requests whose body is CORS-safelisted (multipart, urlencoded, `text/plain`), as oRPC v2 does; C) both. It's a bug, so it can be fixed before the round. Source: `.repos/orpc/apps/content/docs/migrations/from-v1.mdx` ("GET requests are rejected by default").
- Human, 2026-10-16 (decision round, the CSRF hole): "Do what you recommend", so A. The RPC handler answers a multipart `POST` without the `trpc-version` header with `415 UNSUPPORTED_MEDIA_TYPE`, before reading the body. `httpLink` sends the header on every request; a form can't add one, and a cross-origin `fetch` that does needs a CORS preflight.
- (agent) The v11 interop handler can't require a header, since v11 clients send none, so it refuses `Sec-Fetch-Site: cross-site` requests whose body a form or a no-cors `fetch` can send (multipart, or no `content-type`) with `403 FORBIDDEN`, as oRPC v2 does. Browsers without `Sec-Fetch-*` (before 2023) aren't covered there; v11 had the same hole.
- Open: the OpenAPI handler takes urlencoded and multipart bodies by design (REST clients and HTML forms), so its mutations rely on `SameSite` cookies or the app's auth. A `Sec-Fetch-Site` option there is the candidate if that isn't enough.
- Lives in: `packages/trpc/src/server/handler/fetch.ts` (`middleware` option), `src/http/index.ts` (`cors`, `toHttpEffect`); tests in `packages/trpc/src/http/core.test.ts`, `packages/trpc/src/server/sockets/websockets.test.ts`; the CSRF rule in `src/server/handler/fetch.ts` (`readInput`) and `src/interop/handler.ts`, tested in `packages/trpc/src/server/handler/files.test.ts` and `interop-v11.test.ts`.
