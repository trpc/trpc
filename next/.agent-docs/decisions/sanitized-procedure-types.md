# A built procedure's type carries only what is read outside it (human asked)

- Human, 2026-11-01: "one thing that we did quite well in v11 was to sanitize procedure so the built procedure only contained things that are needed to infer stuff outside / this makes it so that .d.ts files etc gets less noisy etc (no ctx etc) / can we do the same for v12? i think we don't need all of those things once the proc is built?"
- (agent) A built procedure is a `QueryProcedure<D>`, `MutationProcedure<D>` or `SubscriptionProcedure<D>` (aliases of `Procedure<D, 'query'>` and so on; the type moved from the def to `Procedure`'s second argument). `D` always has `input`, `output` and `errors`, and only the others that say something:
  - `ctx`, unless `{}`: the fetch, interop, OpenAPI and MCP handlers, `createRouterClient`, `call()` and actions type `createContext`/`ctx` from every procedure's (`inferRouterContext`). v12 routers are plain objects, so there is no router root to carry it, as v11's did.
  - `services`, unless `never`: the same handlers type `layer`/`runtime` from it (`inferRouterServices`).
  - `outputValidated: true` and `declared` (the codes `.errors()` lists, no longer the map of errors), only when an output schema validates: `experimental_validationLink({ contract: appRouter, output: 'json' })` takes a router as its contract and decodes those outputs and those codes' `data` ([`validation-link-decoded-types.md`](./validation-link-decoded-types.md)).
  - Gone: `meta` (nothing reads a built procedure's meta from its type; a contract's is `contract.meta`) and `type` (on `Procedure`).
  - `byId` in a declaration was `Procedure<{ type: 'query'; ctx: Context; meta: {}; input: …; output: Post; errors: …; services: never; outputValidated: never; declared: {} }>` and is `QueryProcedure<{ input: …; output: Post; errors: …; ctx: Context }>`. An implemented contract procedure printed `ImplementedProcedure<ImplementerDef<With<RootDef<…>>, ContractWith<…>>, ContractProcedure<…>, never>`; it prints the same flat def. `hover.test.ts` locks the printed forms.
- Why this formulation: the def is a member of an interface of the eight combinations (`ReturnShapes` for queries and mutations, `DefShapes` over `DefFields` elsewhere), picked by `ShapeKey<keyof ctx, servicesKey, outputValidated>`. Interface members are worked out when read, and the key's arguments are types many procedures share, so each combination's checks run once. Measured before it, on `pnpm bench shapes` (1,500 procedures, server half, `plain` 349 instantiations per procedure on `v12`): a key-filtering mapped type 687; a conditional alias over seven field arguments 486 (an alias instantiates its arguments for every instantiation, where an object literal's members wait to be read); `services` checked through `Exclude` +34. `QueryProcedure` as an interface extending `Procedure` cost +14% to a handler reading 1,000 procedures from `.d.ts` (compared member by member against `AnyProcedure` where an alias of `Procedure` compares type arguments), and prints the same.
- `servicesKey` is `requires | ServicesKey<$Ret>`: a resolver's services without `Awaited` unless it returns a promise. Every procedure in a program pays the key, read or not; with `SplitReturn<$Ret>['services']` a client checking a router from source paid 6% more. It is `never` whenever `services` is, so a needed service is never left out; when the only requirements are `Scope` or provided services it says `services: never`.
- Cost against `v12` before:
  - `pnpm bench shapes`, instantiations per procedure: server half +2 to +15% (`plain` 349 → 386, `output` 591 → 607, `middleware` 1,013 → 1,058, `contract` 1,289 → 1,312, `effect services` 357 → 411); with the client +2 to +9%. Memory +4 to 5%, check time within noise to +10%.
  - `spikes/big-routers` (1,000 procedures, zod, mostly `async` resolvers): the server from source 891,013 → 890,953 instantiations; a client checking the server's source 772,390 → 844,846 (+9%); reading the declarations, the apps 29,643 → 30,957 (+4%), the fetch handler 63,976 → 73,029 (+14%, 0.03 → 0.04s), `dts-split` 47,885 → 51,899.
  - Declarations: a big-routers domain 69,599 → 59,021 bytes (−15%); `examples/monorepo`'s packages 11,615 → 6,716 bytes (`billing`, implemented from a contract, 5,542 → 1,218).
- Lost: `ProcedureDef`'s fields are optional; whole-router reads index them as `D[F & keyof D]` (+4k instantiations at 1,000 procedures). `meta` on a procedure's type.
- Human, 2026-11-01, on always printing `services` (`services: never` on most procedures, which would take the client-from-source cost from +9% to about +3%): "no".
- Human, 2026-11-01, on printing `SchemaValidationError<{ id: string }, z.core.$ZodIssue>` instead of `SchemaValidationError<z.ZodObject<{ … }, z.core.$strip>>` (keyed by the input and an issue family rather than the schema, which types the issues lazily: [`zod-and-effect-input-issues.md`](./zod-and-effect-input-issues.md)): "doesn't matter". It stays as is.
- Human, 2026-11-01: "i still see ctx in the hover which will cause bloat in dts files".
  - (agent) What it costs: `ctx: import("@big/base").Context;` once per procedure, twice in a domain whose index re-exports its files. In `spikes/big-routers` (1,000 procedures) that is 88 KB of 1.19 MB of declarations (7%); nothing when the ctx is `{}`.
  - (agent) Any type a procedure's own type carries is printed in its declaration, so `ctx` leaving the procedure means it lives on the router, or nowhere. The per-procedure readers can't use a router: `call(byId, input, { ctx })` (`CallOptions`) and the action factories (`Fits`) check `ctx` against one procedure, and a standalone middleware's ctx needs ([`keep-t-object.md`](./keep-t-object.md)) differ by procedure.
- Open:
  - Where `ctx` goes, if not on the procedure:
    - A) On the root router, as in v11: `t.router(routes)` brands the plain object with `t`'s ctx, type only. Handlers, `createRouterClient` and `localLink` type `createContext` from the brand. An unbranded root is a type error at the handler, or its `createContext` goes unchecked. `call()` and action factories lose the ctx check, or take it from `t` (`t.call`, a factory made from `t`). Procedures from another `t`, and a middleware's ctx needs, are checked only if they still print on the procedures that have them.
    - B) Nowhere: `createContext`, `call()` and actions are typed by what they're given, and a wrong ctx is found at runtime.
    - C) Keep it, printed by name when the ctx type is named (`ctx: Context`).
  - A contract's own procedures still print `ContractProcedure<'query', ContractWith<…>>`: `implement()` reads the builder state.
- Lives in: `packages/trpc/src/server/procedures/procedure.ts` (`ProcedureDef`, `Procedure`, `QueryProcedure`, `MutationProcedure`, `SubscriptionProcedure`, `ProcedureOfType`, `ShapeKey`, `DefFields`, `DefShapes`, `BuiltDef`, `ProcedureTypeOf`, `DefCtx`, `DefServices`), `builder.ts` (`ReturnShapes`, `ReturnDef`, `ServicesKey`, `StreamFields`), `implement.ts` (`ImplementedFields`), `router.ts` (`DefField`), `src/contract/index.ts` (`ContractProcedureDef`), `src/client/types.ts` and `src/effect/index.ts` (the type from `Procedure`), `src/server/caller.ts`, `src/actions/index.ts`, `src/server/procedures/hover.test.ts`.
