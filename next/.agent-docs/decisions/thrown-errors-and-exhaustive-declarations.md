# Thrown errors keep their code; declared errors are exhaustive (human)

- Human, 2026-10-19, on how thrown errors reach the client: "on errors, do number 2 but an opt-out for warning for thrown errors / declaration is not a _must_, but if it is declared it should be exhaustive and enforce procedures to only return/throw those - should could be caught as type errors if its not too costly".
- Human, 2026-10-19, on whether built-in codes should be `matchError()` keys (A: no, B: optional keys, C: any code): "D) i think we already covered this? the types should rule it, and if it's inferred we should still have it in the match and if its declared that's the only types that the producere _can_ return without type errors.. ... there's always a "catch all" unexpected error but we should do our best outside of that to be exhaustive".
- Before both, 2026-10-18: "maybe if something is missed as its `throw`n instead on the server it should get into some of the "catch all" things on the cleint if it isn't unhandled... ideally with some sort of dev warning that we're throwing an error that could be `return`ed - probably a common hiccup for people coming from v11".
- Without `.errors()`, a thrown `TrpcError` with a custom code keeps its code, message and `data`, `defined: false`. This replaces [closed-client-errors](./closed-client-errors.md)' masking for those procedures. A thrown built-in code still keeps its code and loses its `data`.
- With `.errors()`, the list is exhaustive:
  - Returning or failing with an error it doesn't list, or with `data` of another type, is a type error (`DeclaredCheck`, `DeclaredStreamCheck`). Contract implementations already had `UndeclaredCheck`.
  - (agent) So is a query's or mutation's streamed `Stream` failing with one, with or without `.output(stream(Item))`: its failures are the procedure's errors ([streamed-output-errors](./streamed-output-errors.md)), so `DeclaredCheck` sees them with the rest.
  - A thrown custom code it doesn't list is an `INTERNAL_SERVER_ERROR` (a crash, masked in production).
  - A thrown error with a listed code is typed, even without its constructor, and its `data` is validated.
- `matchError()` keys follow the types (the D answer): every inferred or declared code is a required key. Since [exhaustive-match-error](./exhaustive-match-error.md), so is every link code, and the rest go to one required `unexpected`.
- When `NODE_ENV` is `development`, a procedure that throws a `TrpcError` it could return logs an Effect warning, once per procedure and code, hinting that v11's `throw new TRPCError()` is `return error()` now. `initTrpc({ warnThrownErrors: false })` turns it off.
- (agent) The reading of "number 2", relayed by the coordinator: a thrown custom code from a procedure without `.errors()` reaches the client, untyped, and lands in `matchError()`'s `unexpected`.
- (agent) On the client it is an `UndeclaredError`, a third member of `ClientError`. Its code type is `` `~undeclared:${string}` ``, so no literal matches it: `switch (err.code)` cases and `err.code === 'NOT_FOUND'` leave it out, and only `default` and `unexpected` see it. A branded `string & {…}` still narrowed into `case 'NOT_FOUND'`.
- (agent) The opt-out is per root (`initTrpc`), not per procedure: a procedure can opt out by returning its errors. The warning about a thrown code that `.errors()` don't list ignores the opt-out, since that error turns into a crash.
- (agent) The warning is for `development` only, not `test` (unlike `exposeUnexpectedErrors`), to keep test output quiet. It is an `Effect.logWarning`, so it goes through the handler's `layer` loggers. It is server code, so client bundles don't grow.
- (agent) Only a declared code makes a thrown error typed, whether it came from the declared constructor, a `TrpcError.Tagged` class or `new TrpcError()`: a thrown `TrpcError.Tagged` class nothing declares, or another procedure's constructor, is untyped like any thrown code, since the client's union can't list it. Warnings skip declared codes, returned errors and crashes. Thrown errors in middleware, in a subscription's stream and in a query's or mutation's streamed output (a returned `AsyncIterable` or `Stream`) follow the same rules as in the resolver.
- (agent) Links still turn a custom code they made themselves into `CLIENT_ERROR`. Only errors the server sent (`keepUntyped`) pass through as they are.
- (agent) Type-check cost, on 1,500 generated procedures with tsc 7: with `.errors()`, +22% instantiations, +10% memory and about 0.1 ms more per procedure; without it, +2% instantiations and no measurable time. Four other shapes cost more and were dropped.
  - (agent) Re-measured with `pnpm bench shapes` against the commit before (`946729e18`): `.errors()` +13% instantiations and +10% memory, `.errors()` with `.output()` +8%, no `.errors()` +4%; `pnpm bench typecheck` +2.6%. `DeclaredCheck` is about a third of the time `.errors()` adds. With the cheaper output check since, `.errors()` with `.output()` checks faster and in less memory than before this work ([`type-check-shapes.md`](../notes/type-check-shapes.md)).
- Why: v11 code throws its errors, and masking a thrown custom code hid what the server meant. A declared list that the types and the runtime both hold to makes `matchError()`'s keys a complete list of the procedure's errors.
- Lost:
  - `ClientError` is no longer only literal codes: `UndeclaredError`'s code is a pattern type, and its `data` is `unknown`.
  - A thrown custom code from a procedure without declarations is no longer masked, so its message and `data` reach clients in production.
  - Errors from middleware aren't checked against `.errors()`.
- Open: per-procedure opt-out of the warning. Promises and iterables nested inside an output (`{ comments: promise }`) skip these rules: a `TrpcError` they reject with is sent as it is, since serializers settle them synchronously and declared `data` can't be validated there.
