# The docs site's build caches what it can and compiles the rest in three processes (human asked)

- Human, 2026-10-20 (via the coordinator): "looks like v12 is taking a lot of time to deploy on vercel which famously fast, can you try to optimize it? i think caching is key, maybe using cached server loaders or something for shiki(?) idk. i know raf-query did some stuff to speed up samples. make it fast".
- (agent) Where the time went, on Vercel's build machine (4 cores, 8 GB): a production build that changed a workspace package or the lockfile spent 11–15 minutes in Vite's transform, compiling the ~590 Twoslash blocks one at a time on the main thread. A warm one took 138 s from start to ready, with a 51 s transform, 35 s of social cards and 10 s of ignore step. Highlighting was already cheap: Shiki's languages load lazily, and raf-query's notes (`www-twoslash-cache.md`, `vercel-ignore-build-step.md`) describe the cache and ignore step this site already had. So the fix is to compile fewer blocks, then compile the rest in parallel.
- (agent) Fewer blocks recompile. A block's cache key had the whole `pnpm-lock.yaml`'s hash, so any dependency change anywhere recompiled every block. Now it has the lockfile closure of the block's sample app: its importer's dependencies, through `link:` workspace packages, aliases and snapshots, transitively, with the linked packages' `exports`/`types` fields. It also has the closure of www's `@shikijs/twoslash`, `twoslash` and `typescript6`, so a compiler upgrade still recompiles. A block that read an installed package outside its closure, or failed to resolve an import (2307, 2688, 2792, 7016), keeps the whole lockfile as a dependency. Workspace sources a block read are fingerprinted by their declarations (`transpileDeclaration`) and import specifiers, so an edit inside a function body keeps the cache. A file `isolatedDeclarations` can't describe falls back to its text. Over the 150 commits before this, 31 of the 77 that touched a block's source dependency now keep the cache. The other 46 changed a declaration, and those still recompile: every v12 block reads all of `@trpc/server`'s sources, so an `@internal` signature change (`portMessages`, 6865d75) recompiles all 213 v12 blocks.
- Human, 2026-10-20 (via the coordinator): "Fix the Twoslash cache key so www dependency changes don't recompile every block."
- (agent) The lockfile fallback still caught most blocks: 394 of 584 entries listed the whole lockfile, so a dependency added anywhere (d36e59e added one to `www`) recompiled 395 of 593 blocks. They read two packages outside their closure through pnpm's hoisted links (`node_modules/.pnpm/node_modules/<name>`): `happy-dom` imports `buffer` and `@hey-api/openapi-ts` imports `ofetch` without depending on them. Such a block now lists where each link it could have been found through (beside the store, and at the workspace root) pointed, and its packages' own dependencies (`packagesFrom`) count as reached. It misses when a link moves. A package read outside the closure some other way, or an unresolved import, still lists the lockfile. Locally, adding `yaml` to `tooling/vercel-ignore` and installing took the build from 40.2 s warm to 246.6 s, 395 blocks compiled, and removing it took 252.0 s. With the links it was 39.2 s and 38.5 s, none compiled. No entry lists the lockfile now. Old entries stay valid until the lockfile next changes, which recompiles them once.
- (agent) The rest compile in parallel. During a build, `docsContent` renders pages in child processes (`build/render-pool.ts`), one per core but the build's (3 on Vercel), and dev still renders in-process. A process gets the pages of the sample apps it compiled last, to reuse its TypeScript environments. They're processes, not worker threads: `--max-old-space-size` in `NODE_OPTIONS` (the build's 4 GB) overrides a thread's `resourceLimits`, and threads' heaps grew past 2 GB each, 8.9 GB resident in all. Each process has a 1280 MB heap and keeps 2 TypeScript environments (`liveEnvironments`, 3 before). A cold build then peaks at 6.1 GB resident, as the one-thread build did. The processes end at `buildEnd`, before Rolldown renders chunks, which is most of a build's memory. A process that dies is replaced and its page retried once.
- (agent) Smaller costs, each measured with a CPU profile of a warm build:
  - Social cards. resvg was 76 of the 90 ms a card took, one card at a time. A card's PNG is now kept in `node_modules/.cache/og` under the hash of resvg's version, the raster options and the SVG, and misses rasterise with `renderAsync`, one per core: 23 s became 2 s warm and 9 s cold.
  - Commit dates. A `git log -1` per page, forked from the build's large process, took about 10 s of the main thread. One `git log` per docs folder replaces them. For the v12 pages, whose dates skip renames, it's the repo's log with rename detection, followed back through each page's names. The dates are the same on the full history and on a 10-commit clone.
  - Popup types. Twoslash highlighted each hover's type on its own, 14,329 times a build for 5,999 different types (about 15 s). Each highlight is now memoised per process, and every hover gets a copy.
  - One block missed every build, because its own `// @filename:` file under `node_modules` counted as an installed dependency.
  - The ignore step failed in Vercel's 10-commit clone whenever the previous deployment's commit was further back ("fatal: bad object"), so those deployments built. It now fetches that commit (depth 1). Changes to `packages/**/*.test.ts(x)` don't build either: the site compiles the packages' sources, never a test.
  - CI's `www` job caches all of `node_modules/.cache`, per commit, restoring the latest.
- (agent) Local timings, 4 cores, same tree, `NODE_OPTIONS=--max-old-space-size=4096 pnpm build`, before → after:
  - Warm (everything cached): 78.2 s → 31.0 s. Transform 30.5 → 13.3 s, social cards 22.7 → 1.9 s, SSR and prerender 18 → 11 s.
  - Cold (empty cache): 494 s → 251 s. Transform 446 → 225 s, social cards 23 → 9 s.
  - The output is the same 1,027 files as before, byte for byte, with `pages.json`'s build time blanked: pages, `.md` twins, `llms.txt`, sitemap with its `lastmod` dates, social cards, and Twoslash hovers and errors. That holds both for this change and for rendering in processes against in-process on the same tree.
- (agent) Vercel, same machine, start to ready:
  - Warm, before: 138 s (71fa772).
  - Cold cache, one thread (a7d7f65, the first build with the new key): 958 s, with an 883 s transform. That's about what a cold build cost before (998 s, 3e69331).
  - A package declaration change, 213 blocks recompiled, before the processes (6865d75): 730 s, with a 679 s transform.
  - The same change and cache with the processes (3aedf56): 358 s, with a 302 s transform. Its other phases were clone 2 s, ignore step 11 s, install 4 s, config 4 s, social cards 4.5 s, SSR and prerender 17 s, output 4 s and deploy 6 s. Saving the build cache (about 80 s) comes after "Deployment completed" and doesn't delay it.
- Why: a deployment that changed a package rebuilt hundreds of blocks whose types hadn't changed, and the ones that had to compile used one of four cores. The caches keep the output identical, because each key is what the output is made from: the block, the declarations and lockfile entries it read, and the compiler.
- Lost: a block now recompiles only when something in its key changes, so anything that changes its output from outside the key ships stale until the entry ages out (14 days unused). The declaration fingerprint covers a source's types, and the hoisted links and the lockfile fallback cover packages a block reads outside its closure. A block that reads a closure package through a hoisted link ships stale if the link moves to a version outside the closure, as before. Builds also need three child processes and about 6 GB, so a smaller build machine needs `makeRenderPool`'s size lowered. A warm build is about 2 s slower than rendering in-process, since each process starts and reads the cache.
- Not done: ignoring JSDoc in fingerprints would keep 7 more of the 150 commits' caches, but hovers show JSDoc, so a stale one would ship. Finer keys (only the declarations a block uses) would stop an `@internal` change from recompiling every v12 block, but they need the type graph that compiling the block gives.
