# `experimental_byteStream()` inputs are `application/octet-stream` bodies over OpenAPI too (agent)

- Closes the Open bullet of [`byte-stream-inputs.md`](./byte-stream-inputs.md) (human) that "the OpenAPI handler and `experimental_generateOpenApi` don't know byte stream inputs". Streaming an upload to a REST route (`PUT /videos/{id}` with `application/octet-stream`) is what users of the OpenAPI handler expect.
- `experimental_createOpenApiHandler` hands a byte stream input the `application/octet-stream` body unread, as the RPC handler does: `maxBodySize` doesn't apply and the schema's `maxBytes` does. A byte stream route answers any other body with `415 UNSUPPORTED_MEDIA_TYPE`, and other routes still refuse `application/octet-stream`. The procedure decides, through its input schema (`byteStreamPart` in `byte-stream.ts`), so a handler built from a `contract` streams too.
- With `inputStructure: 'detailed'`, the `body` field of a `Schema.Struct` input can be the stream, so a route takes path params, the query and headers next to it. With the default compact structure, only the whole input can be one, so such a route takes no path params.
- A resolver that stops reading early still gets its response out on Node: the OpenAPI handler is only a web handler, so behind `serve()` or an adapter its `Request` wraps Node's, and cancelling that body closed the socket. The handler drains the rest instead (`drainingBodyStream`), as the RPC handler does on Node.
- No `trpc-version` header is needed, unlike the RPC handler. `application/octet-stream` isn't a CORS-safelisted content type, so another site's page can't send it without a preflight. The CSRF guard lets it through as it does JSON, which changes the allowlist in [`openapi-csrf-guard.md`](./openapi-csrf-guard.md).
- The byte stream's `ReadableStream` side has a `toCodecJson` link to `{ type: 'string', format: 'binary', contentMediaType: 'application/octet-stream' }`, with decode and encode forbidden (JSON can't carry a stream). Effect's JSON Schema compiler drops a declaration's own annotations, so this link is how contracts and documents describe the bytes instead of `{}`, nested in a struct too.
- `experimental_generateOpenApi` and `experimental_generateOpenApiFromTypes` document the whole input, or a detailed input's `body`, as `requestBody: { required: true, content: { 'application/octet-stream': { schema: { type: 'string', format: 'binary' } } } }`. `target: 'rpc'` documents a `POST` (queries too, as `httpLink` sends them) with a required `trpc-version: 12` header, and leaves out a procedure whose stream is a detailed `body`, since the RPC endpoint can't take one.
- `experimental_openApiLink` sends a `ReadableStream` input, or a detailed input's `body`, as the body itself with `duplex: 'half'`.
- Why: the RPC wire already settled the body (raw octets, read as pulled). OpenAPI's standard spelling for raw bytes is that `requestBody`, which generated clients send as is.
- Lost:
  - A `Blob` passed to `experimental_openApiLink` for a byte stream: the client type is `ReadableStream<Uint8Array>`, so pass `blob.stream()`.
  - Path params next to a compact byte stream input.
  - The guard's "only JSON skips" rule: `application/octet-stream` from any origin now reaches `cors()` and the route, like JSON. A route that doesn't take a byte stream refuses it with a 415.
- Open: a stream nested anywhere but a detailed `body`, as for RPC.
- Lives in: `packages/trpc/src/server/validation/byte-stream.ts` (`byteStreamPart`, the `toCodecJson` link), `src/server/handler/body.ts` (`drainingBodyStream`), `src/openapi/handler.ts` (`readStream`), `src/openapi/rest/csrf.ts`, `src/openapi/generate.ts` (`byteStreamBody`), `src/openapi/link.ts`, tests in `src/openapi/byte-stream.test.ts`, `src/openapi/document-contract.test.ts` and `src/openapi/typescript.test.ts`, docs in `www/docs/server/byte-streams.md#over-openapi`, `www/docs/openapi/routes.md`, `document.md` and `client.md`.
