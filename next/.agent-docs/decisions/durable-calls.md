# `durable()` keeps query and mutation results by call id on Effect's `BackingPersistence` (agent)

- Answers, with the Effect-native lean and pending a human, the Open (human) in [`builder-and-procedures.md`](./builder-and-procedures.md): "mutations and queries that return something we can subscribe to too (make it durable for res cancellations)".
- (agent) `durable<{ ctx }>({ key?, ttl = '10 minutes', claimTtl = '30 seconds', pollInterval, serializer? })` in `trpcdev/middleware` is Effect middleware that requires `Persistence.BackingPersistence` (`effect/persistence`), so stores are Effect's layers (memory, Redis, SQL, KeyValueStore), as for `rateLimit()` ([`rate-limit-on-effect-ratelimiter.md`](./rate-limit-on-effect-ratelimiter.md)) and the publisher guides ([`publisher-backends.md`](./publisher-backends.md)). No trpcdev store interface.
- (agent) The key defaults to `${path}:${callId}`, `callId` being the `trpc-call-id` request header (1–128 of `[\w.:-]`, else `BAD_REQUEST`). `key` overrides it (scope by user; key by input over WebSockets, which have no per-call headers). No header, no durability: the call runs as usual.
- (agent) The rest of the chain runs in a detached fiber (`Effect.forkDetach`) that the request joins, so an interrupted request (client gone) leaves it running; it writes the result when done. Calls running on the same instance share a `Deferred`; another instance sees a `running` claim (refreshed every `claimTtl / 2`) and polls, or runs the call itself once the claim expires. No atomic claim exists in `BackingPersistence`, so simultaneous starts on two instances can both run (said in the docs).
- (agent) Kept: successes (serialized with the default serializer) and typed errors (`defined`, with their status). Not kept: unexpected errors (a retry should run again), streamed outputs (async iterables, `Stream`s, promises). Each entry holds a SHA-256 of the serialized input; the same id with another input fails with `CONFLICT`. Hence `.use(durable())` goes after `.input()`.
- (agent) A replay returns `ok(value)`, so output validation runs on it as on a fresh result.
- (agent) `durableLink({ retries = 3, delayMs })` in `trpcdev/client` gives mutations (and `{ durable: true }` queries) a `crypto.randomUUID()` call id (or the call's `callId` option, for picking up after a reload), sends it as a header with `batch: false`, and retries network failures and 5xx with the same id.
- (agent) To make the header readable, calls on HTTP and sockets now get the request as Effect's `HttpServerRequest` service (`RunOpts.request` in the handler core); in-process calls still have none ([`http-core-on-effect-http.md`](./http-core-on-effect-http.md)). Middleware reads it with `Effect.serviceOption`.
- (agent) "Something we can subscribe to": streamed and long-running work is a mutation that returns an id plus a `Publisher` channel the client subscribes to with `lastEventId`, which already resumes (memory buffer, Redis, hibernating Durable Objects). The docs show it; no second mechanism.
- Lost: resuming a streamed output mid-stream; headers and status of the first response on replay; exactly-once across instances; the resolver's `signal` still aborts when the client leaves.
- Lives in: `packages/trpcdev/src/server/durable.ts`, `src/middleware/index.ts`, `src/client/links/basic.ts` (`durableLink`), `src/server/core.ts` (`request`), `src/internal/protocol.ts` (`HEADER.callId`), `test/integration/durable.test.ts`, `docs/procedures.md` (after `rateLimit()`).
