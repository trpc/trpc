# `durable()` keeps query and mutation results by call id on Effect's `BackingPersistence`, streamed outputs too (human)

- Answers the Open (human) in [`builder-and-procedures.md`](./builder-and-procedures.md): "mutations and queries that return something we can subscribe to too (make it durable for res cancellations)".
- (agent) `durable<{ ctx }>({ key?, ttl = '10 minutes', claimTtl = '30 seconds', pollInterval, serializer? })` in `@trpc12/trpc/middleware` is Effect middleware that requires `Persistence.BackingPersistence` (`effect/persistence`), so stores are Effect's layers (memory, Redis, SQL, KeyValueStore), as for `rateLimit()` ([`rate-limit-on-effect-ratelimiter.md`](./rate-limit-on-effect-ratelimiter.md)) and the publisher guides ([`publisher-backends.md`](./publisher-backends.md)). No @trpc12/trpc store interface.
- (agent) The key defaults to `${path}:${callId}`, `callId` being the `trpc-call-id` request header (1–128 of `[\w.:-]`, else `BAD_REQUEST`). `key` overrides it (scope by user; key by input over WebSockets, which have no per-call headers). No header, no durability: the call runs as usual.
- (agent) The rest of the chain runs in a detached fiber (`Effect.forkDetach`) that the request joins, so an interrupted request (client gone) leaves it running; it writes the result when done. Calls running on the same instance share a `Deferred`; another instance sees a `running` claim (refreshed every `claimTtl / 2`) and polls, or runs the call itself once the claim expires. No atomic claim exists in `BackingPersistence`, so simultaneous starts on two instances can both run (said in the docs).
- (agent) Kept: successes (serialized with the default serializer) and typed errors (`defined`, with their status). Not kept: unexpected errors (a retry should run again). Streamed outputs are kept as frames over unbatched HTTP (below), and not kept over other transports. Each entry holds a SHA-256 of the serialized input; the same id with another input fails with `CONFLICT`. Hence `.use(durable())` goes after `.input()`.
- (agent) A replay returns `ok(value)`, so output validation runs on it as on a fresh result.
- (agent) `durableLink({ retries = 3, delay })` in `@trpc12/trpc/client` gives mutations (and `{ durable: true }` queries) a `crypto.randomUUID()` call id (or the call's `callId` option, for picking up after a reload), sends it as a header with `batch: false`, and retries network failures and 5xx with the same id.
- (agent) To make the header readable, calls on HTTP and sockets now get the request as Effect's `HttpServerRequest` service (`RunOpts.request` in the handler core); in-process calls still have none ([`http-core-on-effect-http.md`](./http-core-on-effect-http.md)). Middleware reads it with `Effect.serviceOption`.
- (agent) "Something we can subscribe to": streamed and long-running work is a mutation that returns an id plus an `experimental_Publisher` channel the client subscribes to with `lastEventId`, which already resumes (memory buffer, Redis, hibernating Durable Objects). The docs show it; no second mechanism.
- Lost: headers and status of the first response on replay; exactly-once across instances; the resolver's `signal` still aborts when the client leaves.
- Human, 2026-10-16 (decision round, on keeping this as built or making streamed outputs resumable mid-stream): "Spike it". Kept as built; mid-stream resume of a durable streamed output is a spike.
- (agent) Spiked, 2026-10-16 ([`../notes/durable-mid-stream-resume.md`](../notes/durable-mid-stream-resume.md)): a frame log on `BackingPersistence` (each frame stored by index, written by a detached fiber) lets a retry with the same call id resume from frame `n` on any instance, nested deferred values included.
- Human, 2026-10-16 (decision round, land it or keep it a spike): "B - under experimental_", then "we gotta make some real cloudflare examples that are actually deployed on cf too in order to get confidence" ([`deployed-cloudflare-examples.md`](./deployed-cloudflare-examples.md)). Landed under the `experimental_` names it already had.
- (agent) Built, 2026-10-16. The HTTP handler provides a frame sink to each unbatched call (`CurrentFrameSink` in `server/execution/frame-sink.ts`, [`handler-services-in-effect-context.md`](./handler-services-in-effect-context.md)); batches, sockets and in-process calls have none, so their streamed outputs still aren't kept, and a retry of a streamed call over them fails with `BAD_REQUEST`.
  - First call: a result `durable()` can't keep as data stays `running` (its claim) until the handler serializes it. The handler then gives the head and chunks to the sink, and a fiber detached from the request writes them to `@trpc12/trpc/durable-frames` (`${key}:${i}` per frame, `${key}:meta` with the count), marks the entry `streamed` and passes each frame on to the response. The output keeps streaming into the store after the client leaves.
  - While it streams, `meta` lives for `claimTtl` and is refreshed, so readers stop when the writer's instance dies; frames and the finished `meta` live for `ttl`.
  - Retry: `trpc-resume-from: n` (default 0) answers with frames from `n` on, polling `meta` every `streamPollInterval` (25 ms) until the last. Output validation is skipped: the frames were validated when they were first written.
  - Client: `durableLink` puts its retry options on the call under a symbol; `httpLink` counts the frames it got and, when the body fails with a lost response, sends the call again with `trpc-resume-from` and feeds the new frames into the same deserializer. Open deferred values settle from the new response, from any instance.
  - Publisher channels stay the way to follow long-running work across sessions; this covers a dropped connection during one call.
- (agent, 2026-10-19) Fixed: two calls with the same id that started together on one instance could both run it when the store answers asynchronously (Redis): the in-flight check and the claim were separated by the store's read. The check is repeated after the read, and the claim is made in the same synchronous step. Input fingerprints are `Effect.fnUntraced`, with `Effect.promise` only around `crypto.subtle.digest` ([`effect-internal-patterns.md`](./effect-internal-patterns.md)).
