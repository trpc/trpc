# The examples load the assignee by issue id (human asked, agent designed)

- Human: fix the issue page's waterfall ("you need like an issue/x/author"). The page `await`ed the issue to learn `assigneeId`, then fetched `GET /api/users/:id`: two db round trips in a row before the card rendered.
- **`GET /api/issues/:id/assignee`** (`getIssueAssignee` in `@examples/db`, one round trip like a join; 404 when the issue doesn't exist). Each app's `assigneeQuery({ issueId })` is keyed `["issues", "assignee", issueId]`, so the Next server component and the Start loader `prefetch` it with the id from the URL, beside the issue and comments. It resolves `null` on that 404 (`parseFound`) instead of calling `notFound()`: the issue query already 404s the page, and a rejected prefetch would reach the browser as a second, uncaught error on Start's not-found page. "Author" in the request meant the assignee: comment authors are already embedded in each comment.
- `GET /api/users/:id`, `getUser` and `UserId` are gone; nothing else read a user by id.
- Lost: embedding the assignee in the issue response (one request, but the card couldn't stream separately and the issue query would carry a join it doesn't need everywhere); a per-user cache shared across issues (the old `userQuery` with `staleTime: 60_000`), which saved a request only when revisiting another issue with the same assignee. No example now shows `await qc.fetch` feeding a dependent input; `www/content/request-waterfalls.md` still documents that pattern.
