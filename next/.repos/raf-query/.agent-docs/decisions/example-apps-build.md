# How the examples are built (agent)

- **`examples/.shared/db`** (`@examples/db`) is the fake DB; **`@examples/db/types`** is its client-safe half (Zod schemas, interfaces, `currentUser`). Client code imports only `/types`; the root entry reads `process.env` and the store on `globalThis`, which must stay out of client bundles.
- **No Effect in the example apps or `@examples/db`** (human, 2026-10-12): they show raf-query to people who don't use Effect. When they need a schema library, use **Zod**. Effect stays in the libraries. The one exception is `examples/tanstack-start-effect` (human asked, 2026-10-14), the same app written for Effect users; see [effect-example.md](./effect-example.md).
- Inputs are **Zod schemas** in `/types`. The API's validators and Start's `validateSearch` take the schema directly (Zod implements Standard Schema). Next pages parse `searchParams` with `IssueListInput` (every field is a string enum).
- The issue page (Next server component, Start loader) `prefetch`es the assignee by issue id beside the issue (`GET /api/issues/:id/assignee`), so nothing waits on the issue first. Comments embed their `author` (backend returns it with the parent) in both apps, so there's no per-comment lookup.
- Comments list newest first, with the form on top: a new comment must land on the loaded first page, or it vanishes when the optimistic entry settles.
- **The client picks a new comment's id** (`crypto.randomUUID()`, sent in `AddCommentInput`). The `invalidate` refetch lands while the action is still pending, so `useOptimistic` re-applies its update on top of data that already holds the saved comment. The reducer skips ids already present, and the shared id keeps one React key, so there's no flash of two entries. Use the same pattern for any optimistic insert.
- Start: `vite` is overridden to `@voidzero-dev/vite-plus-core` (no `vite` bin), so scripts are `vp build` / `vp dev` / `vp preview`. React Compiler runs via `@rolldown/plugin-babel` + `reactCompilerPreset()`. **Don't name a source file `server.ts`**: it can replace the server entry (500 `serverBuild.fetch` undefined). The `nitro()` plugin builds to `.output/` (`public/` + `server/index.mjs`), or Vercel Build Output in `.vercel/output` when `VERCEL` is set.
- `routeTree.gen.ts` is regenerated on every Start build in its own style, so oxfmt and oxlint both ignore it. Next: `reactCompiler: true`, `transpilePackages` for the workspace packages (their `exports` point at `.ts` source).
- **Settings in the top bar** (human asked): link prefetching, stale time, and database latency, stored in cookies (`link-prefetch`, `stale-time`, `db-latency`) so SSR renders the same choice; **Reset** clears them, drops the query cache, and reloads. Stale time's paired `gcTime` is not a control; see [examples-stale-time.md](./examples-stale-time.md). **Latency is per request, not global** (human): the API reads the `db-latency` cookie into each db call's `{ latencyMs }`, falling back to `DB_LATENCY_MS`, the way a real API reads a session cookie. The browser sends it; server rendering forwards the page request's `cookie` header ([isomorphic-requests.md](./isomorphic-requests.md)). Start changes `defaultPreload` with `router.update` and remounts `<main>` keyed by the setting, since `Link` reads it only while rendering. Next wraps `next/link` as `AppLink`: `false` / `true` / hover-then-`true`. Both apps start prefetch off.
