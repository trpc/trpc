# Effect module layout (agent, human asked)

Human, on the first pass: "query.ts is a bunch of classes with ugly `implements` and custom observers… is this how you write complex effect code well?" The layout now follows `.repos/effect` (`Cache.ts`, `Deferred.ts`, `reactivity/AtomRegistry.ts`):

- **Core's public modules are namespaces** (`export * as Query / QueryCache / QueryObserver / Platform` in `index.ts`), each an interface + `TypeId` + guard (`isQuery`, `isQueryCache`, `isQueryObserver`) + functions. Option and key helpers (`queryOptions`, `hashKey`) stay flat: they're the app-facing API. `import-x/no-namespace` is off (human: "you can kill that lint rule").
- **`Query` is a data type, not a class**: `query.ts` is the public facade (`Query.fetch` is `dual`, the rest data-first); `entry.ts` holds the implementation as a Proto object (`Pipeable.Prototype` + `TypeId`) and functions over it. Each entry stores its command Effects once (`entry.commands`), so `Query.refetch(q)` keeps one identity and the observer's shallow compare holds.
- **`QueryCache` is a `Context.Service`** built by `make(config): Effect<QueryCache, never, Scope>` (closures in `Effect.fnUntraced`, no class) or `layer(config)`. Services use methods; data types use module functions, as in Effect. `make` captures its `Context`, `Clock`, `Platform` and `Scope` into `CacheState`; each entry's `Scope` is a child of the cache's, and entries fork with `Effect.runSyncWith(services)` / `FiberMap.runtime`, so no fiber runs outside the cache's runtime. React's `QueryClient` is the only `Effect.run*` edge: it owns the cache's scope and mounts in child scopes.
- **Time is the `Clock`** (`clock.currentTimeMillisUnsafe()` for sync reads), **the page is the `Platform` reference** (`platform.ts`; default reads `window` / `document` / `navigator` lazily, so React tests' `vi.stubGlobal` still works). Core tests run on `it.effect`'s TestClock with `fakePlatform()` (`test-utils.ts`). React tests keep vi fake timers: `QueryClient` uses the default (live) Clock, which vi fakes.
- Kept on purpose: sync listener sets and microtask batching (`notify.ts`) for `useSyncExternalStore` — `SubscriptionRef` updates through a semaphore and has no sync subscribe; Effect's own `AtomRegistry` keeps plain listener sets for the same reason. The observer's own listener set and `trackedProps` are plain for the same reason.
- **`QueryObserver` is a data type too** (human: "everything until the very edge where we expose apis for react should be effect native"). `observer.ts` holds the interface, a Proto object and the functions; there's no separate facade because nothing else in core uses it. Sync functions for renders (`makeUnsafe`, `getUnsafe`, `getOptimisticResultUnsafe`, `setOptionsUnsafe`, `subscribeUnsafe`, `trackResult`, `trackProp`), Effect ones for Effect code (`make`, `get`, `changes`: a `Stream` of results, like `Query.changes`). While it has listeners, the observer holds a `Scope` forked from its entry's: the query subscription is an `acquireRelease` in it, and the `refetchInterval` poll is a fiber in a `FiberHandle` in it (an interval change replaces the fiber, keeping the subscription). Switching queries or losing the last listener closes it; so does the entry leaving the cache, so a removed entry's readers stop polling. The handle is acquired before the subscription, so closing unsubscribes first, synchronously.
- Rejected for the observer: a scope per subscription with no `FiberHandle` (an interval change would resubscribe, churning `gc` / `observers` events); parenting the subscription on the cache's scope (polling would outlive a removed entry); a `SubscriptionRef` of results (no sync subscribe, see above). React's other internals stay plain: `devtools-store.ts`' microtask batching has no sync Effect equivalent (the same reason as `notify.ts`), and `allKeyed` is a ponyfill of a Promise API, where `Effect.all` would only wrap `Promise.all` in a runtime.
- Not adopted: rebuilding on `effect/reactivity` (`Atom.family`, `swr`, `setIdleTTL`, `Hydration`, `@effect/atom-react`). It covers much of raf-query but is `@stability unstable` and differs on promise identity, handles with data, invalidate-waits-for-refetch and streaming hydration. Worth revisiting if the human wants it.
