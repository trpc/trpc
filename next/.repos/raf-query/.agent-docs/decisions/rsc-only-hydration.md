# RSC apps hydrate only through HydrationBoundary (human asked)

Human: "it doesn't need to be specific for nextjs either.. It can just be an rsc thing", "useWaterfall doesn't need to work on the server, it can render a suspense boundary there", "it's fine to force a hydration boundary everywhere you fetch data in RSC", "don't regress tanstack", "/rsc is better".

- **`QueryProvider` and `HydrationBoundary` come from `@raf-query/react`**; its `react-server` condition picks the `HydrationBoundary` that takes `client` ([hydration-boundary-one-import.md](./hydration-boundary-one-import.md), [query-provider-main-entry.md](./query-provider-main-entry.md)). There is no `/next` or `/rsc` entry and no `next` dependency. The only way server data reaches the browser cache is the RSC payload: Flight carries pending entries' promises, and the request client's `sent` set sends each key once. Lost: the `useServerInsertedHTML` script stream, which needed its own promise protocol and held the HTML open until the server client was idle.
- **Its server client starts no request** (`browser-requests.ts`). `useWaterfall` returns the handle without fetching; `useQuery` on an entry with no data and no request in flight throws `BrowserRenderError`. Its `digest` is Next.js's `BAILOUT_TO_CLIENT_SIDE_RENDERING`, so Next.js reports nothing on the server or in the browser (`isBailoutToCSRError` checks only the digest). Other RSC frameworks see a recoverable error. React has no quiet way to render a fallback on the server. Suspending forever would hold the response open, and throwing from `useWaterfall` could escape above the reader's Suspense boundary, so the reader throws.
- **TanStack Start is unchanged**: a plain `QueryClientProvider` client starts requests during SSR and the router streams them.
- **Newer wins, by `updatedAt`** (`hydration.ts`). A dehydrated pending promise resolves to `{ data, updatedAt }`, the sender's fetch time, so staleness counts from when the server got the data (clocks are assumed synced; epoch ms carries no timezone). The receiver resumes it only when it has no data and no request; otherwise it waits for it and takes it if newer, revalidating if it keeps a stale copy or the sender's request failed. Writing data while the entry's own request runs keeps `isFetching` (`succeed` in `entry.ts`).
- Tests: `ssr.test.tsx` server-renders with `react-dom/server.edge`, returning the digest from `onError` as Next.js does, then `hydrateRoot`s the HTML in happy-dom.
