# Docs samples import real libraries; integration pages are example apps (human)

- **Samples import real libraries and real app code, never stubs of them** (human): `@tanstack/react-router`, `next`, `effect` and so on, and app code a sample leans on (`api.ts`, `queries.ts`) is a real file. Incidental clients a page only names in passing (axios) are a hidden `declare`, not a dependency.
- **A few apps, not one per guide** (human: "maintainability and easy to grok examples"): `quick-start`, `tanstack-start` and `nextjs` walk through an app's files, which a reader copies (see [docs-sample-packages.md](./docs-sample-packages.md)). One app per guide (33 apps, 18 route trees, a dependency per one-off library) was more to maintain than the samples it compiled.
- **The guides' samples are written against the shared apps** (agent): a guide's blocks are files in `www/samples/tanstack-start/src/docs/` (see [docs-sample-fences.md](./docs-sample-fences.md)) that import `~/api.ts` and `~/queries.ts`, and may `declare` the page's own leaf components and values (`Spinner`, `slug`), never a library's API. Leaf components stay per page: their props differ from page to page.
- **Each app is its own TypeScript project** (agent): route trees `declare module "@tanstack/react-router"` globally, so two apps in one program would clash. Each is a workspace package with its own `tsc` (see [docs-sample-packages.md](./docs-sample-packages.md)).
- **Route trees are generated** (agent): `build/sample-apps.ts` runs `@tanstack/router-generator` for each app with `src/routes` at build start, like TanStack Start's plugin. `src/routeTree.gen.ts` is committed so the editor and `tsc` work without a build. The React Router sample's `+types` come from `react-router typegen`, run at build start and by its `typecheck` script.
- **A ` ```sample ` fence naming `app/src/file.tsx#name`** (human asked for a fence of its own; see [docs-sample-fences.md](./docs-sample-fences.md)): `build/snippets.ts` expands it into a `twoslash` block, so the HTML and the agent markdown both see a normal fence. `#name` shows every `// #region name` … `// #endregion` part of the file (VS Code markers); without `#name`, the whole file. `title="…"` overrides the title (the path inside the app, none for `src/docs/`) and `title=""` drops it.
- **The whole file compiles, only the region shows** (agent; like mdBook's `rustdoc_include`): the other lines go between `// ---cut-start---` and `// ---cut-end---`. Region-only includes (VitePress, Vocs, TypeDoc, remark-code-import) compile the region on its own and lose its imports.
- **A block compiles in its file's app** (agent): the folder of `www/samples` that holds it (`appOf` in `build/sample-apps.ts`). The expansion writes the block's `// @filename` from the samples dir, and `build/markdown.ts`'s Twoslash function picks the app from it, reads the app's `tsconfig.json` and hands Twoslash every file in it as `extraFiles`, so a block's program has what `tsc` has (the route tree, which nothing imports). Each block compiles as `<file>.<region>.twoslash.<ext>` next to the file, since Twoslash empties a block's files once it's done.
- **The build logic is Effect** (human): `www/build` reads files and runs commands through `FileSystem`, `Path` and `ChildProcessSpawner`, never `node:fs` / `node:child_process`. Vite's hooks and `vite.config.ts` are the edge that runs it with `NodeServices.layer`, and failures are `ContentError`s naming the file. Each render reloads the apps its blocks use, so an edit to an app file shows up in dev. TypeScript still reads `tsconfig.json` through `ts.sys`, because it resolves `extends` and `include` itself.
- **Example files are linted** with `.oxlintrc.json` relaxing the rules that fight readable samples (key and JSX prop order, `curly`, type assertions, button `type`).
