# The examples put the loader verb in the URL, one route folder per verb (human)

- Human: let the examples switch between the three ways a loader starts a query — "it's about ensure/prefetch/fetch", not REST vs RPC — by putting the choice in the URL (`/prefetch/issues`, `/ensure/issues/3`, `/fetch/issues/3`).
- **Why the URL**: the verb is what the examples exist to show, so it is shareable, survives a reload, and SSR renders with it. A cookie setting would hide it.
- **WET, not a `$verb` param** (human: "each type should be self-contained inside of the route rather than having generic abstractions … a human needs to be able to read the examples and follow along easily"; "we shouldn't have a $verb route in any of the examples, it should just be WET"). Each app has `prefetch/`, `ensure/` and `fetch/` route folders with their own route files and readers. A loader calls `qc.prefetch`, `qc.ensure` or `qc.fetch` itself; a reader calls `useQuery` itself: `use()` on the promise for a `prefetch` handle, the data straight off a `QueryHandleWithData` for `ensure` / `fetch`. Lost: a `startQuery(qc, verb, …)` switch and a `useQueryData` that unwrapped either handle, which hid the one difference the examples show behind casts.
- `ensure/` and `fetch/` differ only in the verb and the loader's comment; `prefetch/` differs in its loaders (no await, plain object of handles) and readers (`use()`). Keep the copies in step by hand.
- Unknown verbs are not-found because no route matches. Bare `/issues…` and `/` redirect to `/prefetch/…`, keeping the search.
- TanStack Start needs `defaultStaleReloadMode: "blocking"`: without it a revisit shows the last loader data and reloads in the background, so `fetch` never visibly waits.
- On a server with a per-request client the cache is empty, so `ensure` and `fetch` wait for the same thing on a full page load. Next.js and React Router render every navigation on the server with a new client, so there `ensure` waits like `fetch` every time; the README and feature map say so.
- Effect app: `ensure` and `fetch` reject with the query's failure rather than handing back a `Result`, so their issue loaders catch `IssueNotFound` and throw `notFound()`. Under `prefetch` the reader's `Result` handles it.
- The header is app chrome, not a route: it reads the verb from the path (`loaderVerbOf` in `@examples/kit/lib/loader-verb`) for its list link and the Loader select (see `examples-header-toolbar.md`).
