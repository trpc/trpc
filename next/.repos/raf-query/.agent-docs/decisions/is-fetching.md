# `isFetching` / `useIsFetching` (agent; keep for compat human asked)

- **Keep `useIsFetching`** for TanStack Query compatibility (human, PR #80). Prefer the router's pending UI for navigations and per-query `controls.isFetching` for background refetches; the hook is for the rare global count. Docs steer there and link the Start / Next variants ([Background fetching indicators](../../www/content/background-fetching-indicators.md), [TanStack Start § Pending UI](../../www/content/tanstack-start.md), [React Server Components § Pending UI](../../www/content/react-server-components.md)).
- **`isFetching(filter?)` / `useIsFetching(filter?)`**, like TanStack's, for that global count: the number of entries with a request in flight, matched with the same `match` as `invalidate` / `reset` / `remove` (no filter → every entry). `QueryCache` has `isFetching` (Effect) and `isFetchingUnsafe` (renders); `QueryClient.isFetching` calls the latter. No Stream variant: `events` plus `isFetching` covers it. The hook is `useSyncExternalStore` on `qc.subscribe` with the count as snapshot; the server snapshot is `0` (TanStack reuses the count), so server HTML and the hydrating render agree whatever is in flight on either side. Cache events fire synchronously, also while another component renders (a `readUnsafe` that starts a fetch), so the hook calls `onStoreChange` in a microtask, once per batch, as `devtools-store.ts` does; calling it synchronously makes React warn "Cannot update a component while rendering a different component" (covered by a test).
