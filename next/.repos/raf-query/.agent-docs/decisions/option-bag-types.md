# Types take a bag, not a list of type arguments (human asked; details agent)

Human: "i don't like how we have so many generics with many positional arguments, i prefer option bags", except where we mimic Effect.

- **Option and data types take one bag**: `QueryOptions<{ data; error?; key?; services? }>`, `InfiniteQueryOptions<{ page; pageParam; error?; key?; services? }>`, `QueryFnResult<{ data; error?; services? }>`, `InfiniteData<{ page; pageParam }>` (`QueryTypes` / `InfiniteQueryTypes` in `packages/core/src/options.ts`). `error` defaults to `unknown`, `services` to `never` and `key` to `QueryKey` through `ErrorIn` / `ServicesIn` / `KeyIn`, so a Promise user writes `QueryOptions<{ data: Post }>` without naming an Effect channel. The bags `queryOptions` / `infiniteQueryOptions` return always name `key` (see [handle-factory-key-types.md](./handle-factory-key-types.md)), so a promise factory hovers as `QueryOptions<{ data: Post; key: readonly ["post", string] }>`. The experimental package does the same for its own `QueryOptions` / `InfiniteQueryOptions` / behaviors; TanStack's types it re-exports stay TanStack's.
- **A promise's error stays `unknown`, and the bag leaves it out** (human). A rejected Promise is a typed failure (`Effect.fail` in `fromQueryFn`, `request.ts`): it reaches `Query.fetch`'s error channel and is retried, so the error is `unknown`, not `never`. `never` would only be honest if rejections became defects, as in `Effect.promise`, but `Effect.retry` doesn't retry defects and `runRequest` logs each as "queryFn died". `queryOptions` / `infiniteQueryOptions` omit `error` from the returned bag when it is `unknown`, and omit `services` when it is `never`, so a promise factory hovers as `QueryOptions<{ data: Post }>`. An Effect `queryFn` keeps its inferred error in the bag, including `never` when it can't fail, and keeps `services` when it needs any. `ErrorOf` / `ServicesOf` still read `unknown` / `never` when the keys are absent (`ErrorIn` / `ServicesIn`).
- **Data types take only the factory**: `Query<TFactory>` and `QueryObserver<TFactory>`. Their data and error were always `DataOf` / `ErrorOf` of the factory, so a separate `TData` / `TError` would only repeat it. The `[TypeId]` variance markers stay, as in Effect, computed from the factory. `DataOf` of the erased `QueryFactory` is `unknown`, so `Query.getUnsafe` on an erased `Query` reads `unknown` data.
- **Kept positional**: `queryOptions` / `infiniteQueryOptions` type parameters (TypeScript can't infer a bag's members from an argument; they exist only for inference, and the docs no longer pass them: annotate `getNextPageParam`'s `lastPage` instead), and Effect's own `<A, E, R>` shapes (`Effect`, `Stream`, `request.ts` / `client.ts` helpers that wrap them).
- `InfiniteQueryOptions` gets its page functions from the internal `PageFunctions<TPage, TPageParam, TResult>` base, not from `TTypes["…"]` members written inline. Typing `queryFn`'s `context` through the anonymous bag fixes `TPage` before `queryFn`'s return is inferred, so an unannotated `getNextPageParam(lastPage)` after it reads `unknown`. Covered by the "infer the page type for a getNextPageParam after queryFn" test.
- A typed `Query<F>` still isn't assignable to the erased `Query`: `QueryHandle`'s conditional `input` makes it invariant in the factory. That's why the module functions stay generic over `TFactory`.
- Lost: inferring the builders from a single `TOptions` parameter (loses excess-property checks on the options object) or a single `TResult` (moves where errors appear, and changes the return-type inference `QueryFactory<TServices>` relies on, see [query-services.md](./query-services.md)).
