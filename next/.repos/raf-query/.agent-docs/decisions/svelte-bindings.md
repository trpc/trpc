# Svelte bindings: runes, getters in, one object of getters out (agent)

- **Svelte 5 runes only** (`.svelte.ts` modules, `$derived`, `$state`, `$effect.pre`), peer `svelte ^5.7.0` for `createSubscriber`. Lost: Svelte 4 stores, like TanStack svelte-query before v6.
- **`useQuery(factory, () => handle, () => options?)`**: the handle and options are getters, so `() => data.post` follows a page's new load data. Always a function, like svelte-query's accessors: a value-or-getter union needs a runtime `typeof` the lint rules reject, and a plain handle would silently stop following props. `useWaterfall` takes `() => input` and returns `() => handle`, which plugs straight into `useQuery`. `useIsFetching(() => filter?)` returns `{ current }` (`createSubscriber`, like svelte-query's `ReactiveValue`).
- **Same result object as Vue, from core's `QueryBinding`** ([query-binding](query-binding.md)): getters for the controls, `promise`, and `data` (the promise's value once settled, or a `QueryHandleWithData`'s `data`). Svelte supplies a `$state` version for `track` / `notify`, `untrack` for cache writes, a `$effect.pre` that calls `syncUnsafe`, and the subscription in `onDestroy`.
- **Cache writes run in `untrack`** (the binding's `untracked` hook): starting a read can notify observers synchronously, and Svelte throws `state_unsafe_mutation` for state written inside markup or a `$derived`. Every read re-syncs the handle itself, so markup that reads before the `$effect.pre` still sees the new query.
- **Server**: no subscription, results computed on read. Svelte's `render()` is synchronous, so the server's HTML has data only for entries the cache already holds: SvelteKit server `load`s `ensure` and return the handle plus `dehydrate(qc)`. `useIsFetching` stays `0` until mount so hydration agrees.
- **Build**: `svelte-package` (ships `.svelte` and `.svelte.js` for the app's compiler; `exports` has a `svelte` condition). Tests live in `test/`, not `src/`, because `svelte-package` copies all of `src` into `dist`.
- **TypeScript 6 in this package**: `svelte-check` and `svelte-package` call TypeScript's JS API, which 7 lacks. That gives the package its own `vite-plus` (peer on `typescript`), whose Vitest isn't the copy `@effect/vitest` is linked to, so tests import from `vite-plus/test`. `pnpm` overrides and `packageExtensions` don't reach peer dependencies, so they can't pin TS 6 for the Svelte tools alone.
- Tests: `@testing-library/svelte`'s `render` without its Vitest plugin (its setup file imports the other Vitest copy); `vite.config.ts` sets the browser condition itself, keeping `development` so hydration mismatches warn. `ssr.server.test.ts` runs in a node environment (server-compiled components) and its HTML is the fixture the browser hydration test hydrates.
- **An experiment, like Vue** (human): `.experimental/svelte/` holds `package/` (`@raf-query/experimental-svelte`, private, `0.0.0`), `sample/` (`@examples/experimental-svelte`) and the draft guide in `docs/`, which the site doesn't build. Its README lists the steps to make it real, including re-adding the www build's `svelte-kit sync` step.
- Lint: React's hook and compiler rules are off for `.experimental/svelte/package`; runes are globals in `.svelte` / `.svelte.ts`.
- Draft docs in `.experimental/svelte/docs/svelte.md`; sample app `.experimental/svelte/sample` (SvelteKit 3: no `svelte.config`, `#lib/*` through `package.json` `imports` since `$lib` is gone, `tsconfig` extends the generated `$app/tsconfig`, which its `prepare` script writes with `svelte-kit sync`). `.svelte` fences render as plain blocks; `svelte-check` is what compiles them.
